Detailed study notes on TypeScript, from setup and basic types to generics, utility types and async code.

How to read these notes
  • Each section explains the concept, then shows code, then lists common mistakes.
  • Parts marked Extra add depth beyond the core topics; you'll meet them in real projects.
  • Error messages are written exactly as TypeScript prints them, so you can recognise them in your editor.
  • A styled version with a sidebar is in the same folder: typescript-notes.html.

1. What is TypeScript?

TypeScript is JavaScript with types added on top. It is a superset of JavaScript: every valid JavaScript program is also valid TypeScript, and TypeScript adds syntax for describing what kind of value each variable, parameter and return value holds.

// JavaScript
let message = 'Hello, TypeScript';

// TypeScript: the same code with a type annotation
let message: string = 'Hello, TypeScript';

The : string part is a type annotation. It tells TypeScript "this variable must always hold a string". If you try to put the wrong kind of value in, you get an error in your editor, before the code ever runs:

let message: number = 'Hello';
// ✗ Type 'string' is not assignable to type 'number'.

Why use it?

Benefit What it means in practice
Catch bugs early Typos, wrong argument types and missing properties are flagged while you type, not in production.
Better editor help Autocomplete, inline docs, "go to definition" and safe renames all work because the editor knows the types.
Self-documenting code A function signature like getUser(id: number): Promise<User> tells you exactly how to use it.
Safer refactoring Change a type, and every place that breaks lights up.
Industry demand Most large JavaScript codebases (React, Angular, Node backends) use TypeScript.

How it runs: compilation

Browsers and Node.js only understand JavaScript. TypeScript code is compiled (also called transpiled) into plain JavaScript by the TypeScript compiler, tsc:

basics.ts  ──tsc──►  basics.js  ──node / browser──►  runs
(types)              (types removed)
Types disappear at runtime

Type annotations are removed during compilation. They exist only to check your code before it runs. TypeScript can't validate data that arrives at runtime (API responses, user input); for that you still need runtime checks (see 14. Type assertions and type guards).

2. Installing TypeScript

Global install

npm install -g typescript   # -g = install globally, so `tsc` works in any folder
tsc --version               # check it worked, e.g. "Version 5.x.x"

Per-project install (recommended)

A global install is handy for experiments, but real projects should pin the TypeScript version inside the project, so everyone on the team uses the same one:

npm init -y                      # create package.json
npm install --save-dev typescript   # or: npm i -D typescript
npx tsc --version                # npx runs the project's local copy
Command Effect
npm init -y Creates package.json with default values.
npm install --save-dev typescript Adds TypeScript to devDependencies. It's a build tool, not needed when the compiled JS runs.
npx tsc Runs the tsc from node_modules, not the global one.
Note

npm install --save typescript also works, but puts TypeScript in dependencies. Since it's only needed to build, --save-dev is the usual choice.

3. tsconfig.json: configuring the compiler

Create it

npx tsc --init

This creates tsconfig.json, which tells tsc where your code is, where to put the output, and how strict to be. Each option in the generated file has a comment and a link to the official docs (typescriptlang.org/tsconfig), where every setting is explained.

A clean starting config

{
  "compilerOptions": {
    /* File layout */
    "rootDir": "./src",
    "outDir": "./dist",

    /* Environment */
    "module": "commonjs",
    "target": "es2020",

    /* Type checking */
    "strict": true,

    /* Other */
    "skipLibCheck": true
  },
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist"]
}

What each option does

Option Value Meaning
rootDir ./src Where your .ts source files live.
outDir ./dist Where compiled .js files are written. The folder structure of src is mirrored.
module commonjs Module system of the output. commonjs produces require / module.exports (classic Node). Other options: esnext, nodenext (modern Node with ES modules).
target es2020 Which JavaScript version to output. Newer syntax is rewritten for older targets (e.g. es5 turns arrow functions into function).
lib e.g. ["es2020", "dom"] Which built-in type definitions are available. Add "dom" for browser APIs like document.
strict true Turns on all strict type-checking options. Always keep this on.
jsx react-jsx Only needed for React (.tsx files).
skipLibCheck true Skips type-checking .d.ts files inside node_modules. Faster builds, fewer errors from third-party types.
include ["src/**/*"] Which files to compile. ** means "any subfolder", * means "any file".
exclude ["node_modules", "dist"] Folders to ignore. Never compile dependencies or your own output.

Why strict: true matters

Without strict mode, TypeScript allows many unsafe patterns, and you lose most of its benefit; it behaves much like plain JavaScript. strict enables a group of checks:

Flag (enabled by strict) What it catches
noImplicitAny Parameters or variables whose type can't be worked out silently becoming any.
strictNullChecks Using a value that might be null or undefined without checking first.
strictPropertyInitialization Class properties that are declared but never assigned.
strictFunctionTypes Passing functions with incompatible parameter types.
useUnknownInCatchVariables catch (err) gives err the type unknown instead of any.
alwaysStrict Emits "use strict" in every output file.
Tip

You configure tsconfig.json once per project. After that, just run tsc.

4. Compiling and running

tsc                      # compile everything in "include" → dist/
node dist/basics.js      # run the output with Node

Project structure after compiling:

project/
├── package.json
├── tsconfig.json
├── src/
│   └── basics.ts
└── dist/
    └── basics.js        ← generated, don't edit by hand

Useful compiler commands (Extra)

Command Does
tsc Compile once using tsconfig.json.
tsc --watch (or -w) Recompile automatically whenever a file changes.
tsc --noEmit Type-check only; don't write any .js. Good for CI.
tsc file.ts Compile a single file. Note: this ignores tsconfig.json.
Note

By default tsc still writes .js files even when there are type errors. Set "noEmitOnError": true to block output while errors exist.

Tools like tsx (npx tsx src/basics.ts) or ts-node run TypeScript directly without a separate compile step, which is convenient in development.

Add scripts to package.json so you don't have to remember the commands:

"scripts": {
  "build": "tsc",
  "dev": "tsc --watch",
  "start": "node dist/basics.js"
}

5. Basic types

Primitive types

let username: string = 'Alice';
let age: number = 27;          // integers and decimals are both `number`
let isAdmin: boolean = true;
Type Holds Examples
string Text 'hi', "hi", `hi ${name}`
number Any number (integer or decimal) 42, 3.14, -1, NaN
boolean True / false true, false
bigint Very large integers 100n
symbol Unique identifiers Symbol('id')
null Intentional "no value" null
undefined Not assigned yet undefined
Lowercase, not uppercase

Use string, number, boolean, never String, Number, Boolean. The capitalised versions are JavaScript wrapper objects and behave differently.

Arrays

Two equivalent ways to write an array type:

let numbers: number[] = [1, 2, 3, 4];
let names: string[] = ['Alice', 'Bob'];

let scores: Array<number> = [90, 85];   // generic syntax, same as number[]

Every element must match the type:

let numbers: number[] = [1, 2, 3, 'hello'];
// ✗ Type 'string' is not assignable to type 'number'.

For arrays that hold more than one type, use a union (section 11): let mixed: (string | number)[] = [1, 'a'].

Tuples

A tuple is an array with a fixed length and a fixed type at each position:

let person: [string, number] = ['Alice', 27];   // position 0 = string, position 1 = number

let wrong: [string, number] = ['Alice', '27'];
// ✗ Type 'string' is not assignable to type 'number'.

Use tuples when position has meaning, for example a coordinate [x, y] or React's useState, which returns [value, setValue].

Extra: you can label positions and make tuples read-only:

let point: [x: number, y: number] = [10, 20];          // labels show up in the editor
const rgb: readonly [number, number, number] = [255, 0, 0];
// rgb[0] = 100;  ✗ Cannot assign to '0' because it is a read-only property.

Enums (quick look)

An enum is a named set of allowed values:

enum Color { Red, Green, Blue }

let favourite: Color = Color.Blue;   // can only be Red, Green or Blue

Enums are covered in depth in 19. Enums.

any: switch off type checking

any means "this can be anything, don't check it":

let randomValue: any = 10;
randomValue = 'hello';   // fine
randomValue = true;      // fine
randomValue.foo.bar();   // also "fine" to TypeScript, but crashes at runtime!
Avoid any

any turns off TypeScript for that value. Errors spread silently, and it defeats the purpose of using TypeScript. Use it only as a last resort (for example, while migrating old JavaScript).

unknown: the safe alternative to any

unknown also accepts any value, but you can't use it until you check what it is:

let userInput: unknown = 5;
userInput = 'hello';        // assigning anything is fine

userInput.toUpperCase();
// ✗ 'userInput' is of type 'unknown'.

if (typeof userInput === 'string') {
  userInput.toUpperCase();  // ✓ inside this check TypeScript knows it's a string
}
any unknown
Accepts any value? Yes Yes
Can you call methods / read properties? Yes, without checks No, not until you narrow it
Can you assign it to a string variable? Yes No, not without a check
Safety None Safe
Use for Escaping the type system (avoid) Values whose type you genuinely don't know yet: API data, JSON.parse, catch errors

void, null, undefined, never

function logMessage(message: string): void {
  console.log(message);       // returns nothing → void
}

let empty: null = null;
let notSet: undefined = undefined;
Type Meaning
void A function returns nothing useful. Returning a value gives ✗ Type 'number' is not assignable to type 'void'.
null Intentionally empty.
undefined Not assigned.
never (Extra) A value that can never happen: a function that always throws or loops forever, or a case that should be impossible (see exhaustiveness checks in section 14). 
function fail(msg: string): never {
  throw new Error(msg);       // never returns normally
}

With strictNullChecks on, null and undefined are not allowed in other types. To allow them, say so explicitly with a union: let name: string | null = null;.

6. Type inference

You don't have to annotate everything. When you assign a value, TypeScript infers (works out) its type automatically:

let inferredString = 'Hello';    // TypeScript infers: string
inferredString = 5;
// ✗ Type 'number' is not assignable to type 'string'.

Hover over a variable in your editor to see the inferred type.

let vs const inference

let a = 'hello';     // type: string      (can be reassigned to any string)
const b = 'hello';   // type: "hello"     (a literal type: it can never change)

const gets a narrower literal type because its value can't change. Literal types are covered in section 12.

When to annotate and when to let TypeScript infer

Situation Recommendation
Variable initialised with a value Let TypeScript infer: let count = 0
Variable declared without a value Annotate: let user: User;
Function parameters Always annotate; they can't be inferred
Function return type Optional, but annotating public or exported functions documents them and catches mistakes
Empty arrays Annotate: const ids: number[] = [] (otherwise the type may be any[] or never[])
Objects matching a known shape Annotate with the interface, to catch typos and missing fields

7. Functions

Parameter and return types

function add(a: number, b: number): number {
  return a + b;
}
  • Each parameter gets a type after the name.
  • The return type goes after the parentheses.
  • Without a parameter type, strict mode reports: ✗ Parameter 'a' implicitly has an 'any' type.

Optional parameters (?)

function greet(name: string, greeting?: string): string {
  if (greeting) {
    return `${greeting}, ${name}`;
  }
  return `Hello, ${name}`;
}

greet('Alice');            // "Hello, Alice"
greet('Alice', 'Hi');      // "Hi, Alice"
  • greeting?: string means the argument may be left out. Inside the function its type is string | undefined, so check it before use.
  • Optional parameters must come after required ones. function f(a?: string, b: string) is an error.

Default parameters

function multiply(a: number, b: number = 2): number {
  return a * b;
}

multiply(5);     // 10
multiply(5, 3);  // 15

With a default, the parameter is automatically optional, and its type is inferred from the default value (b is number).

Rest parameters

function sum(...numbers: number[]): number {
  return numbers.reduce((total, n) => total + n, 0);
}

sum(1, 2, 3, 4);   // 10

...numbers collects all remaining arguments into an array, so its type is an array type: number[].

Arrow functions

const subtract = (a: number, b: number): number => a - b;

Same rules as normal functions; the return type goes after the parameter list.

Function types

You can describe the shape of a function as a type, then assign any function that matches:

type Calculate = (a: number, b: number) => number;

const addFn: Calculate = (a, b) => a + b;       // a and b inferred as number
const divideFn: Calculate = (a, b) => a / b;

let calculate: Calculate;
calculate = add;      // ✓ add(a: number, b: number): number matches

Notice addFn doesn't need to annotate a and b; TypeScript gets them from Calculate. This is called contextual typing.

Function types are especially useful for callbacks:

function fetchData(onDone: (data: string) => void): void {
  onDone('result');
}

Function overloads (Extra)

When a function returns different types depending on its input, overloads describe each case:

function format(value: string): string;
function format(value: number): string;
function format(value: string | number): string {
  return typeof value === 'number' ? value.toFixed(2) : value.trim();
}

The first two lines are the overload signatures callers see; the last one is the implementation.

8. Object types and interfaces

Inline object types

let user: { name: string; age: number } = {
  name: 'Alice',
  age: 27,
};

This works, but writing the shape inline everywhere gets messy and repetitive.

Interfaces

An interface gives an object shape a name, so you can reuse it:

interface User {
  name: string;
  age: number;
}

let user: User = { name: 'Alice', age: 27 };

Optional properties (?)

interface User {
  name: string;
  age: number;
  email?: string;   // may be missing
}

const u1: User = { name: 'A', age: 20 };                       // ✓
const u2: User = { name: 'B', age: 30, email: 'b@x.com' };      // ✓

If email were not optional, leaving it out gives:

✗ Property 'email' is missing in type '{ name: string; age: number; }' but required in type 'User'.

Readonly properties

interface User {
  readonly id: number;
  name: string;
}

const user: User = { id: 1, name: 'Alice' };
user.name = 'New';    // ✓
user.id = 2;
// ✗ Cannot assign to 'id' because it is a read-only property.
readonly is shallow

readonly only stops the property itself from being reassigned. If the property holds an object or array, its contents can still be changed. It's also compile-time only; JavaScript doesn't enforce it at runtime.

Methods in interfaces

interface Product {
  name: string;
  price: number;
  getDiscount(percent: number): number;          // method syntax
  // getDiscount: (percent: number) => number;   // property syntax, same meaning
}

const laptop: Product = {
  name: 'MacBook Pro',
  price: 2000,
  getDiscount(percent) {
    return this.price * (percent / 100);
  },
};

laptop.getDiscount(10);   // 200

Excess property checks (Extra)

When you assign an object literal directly, TypeScript rejects properties that aren't in the type. This catches typos:

const u: User = { id: 1, name: 'A', emial: 'x' };
// ✗ Object literal may only specify known properties, and 'emial' does not exist in type 'User'.

Index signatures (Extra)

For objects with keys you don't know in advance (like a dictionary):

interface Scores {
  [studentName: string]: number;
}

const scores: Scores = { alice: 90, bob: 85 };
scores.charlie = 70;   // ✓ any string key, number value

9. Type aliases

The type keyword gives a name to any type: objects, primitives, unions, tuples or functions.

// object shape, like an interface
type Point = {
  x: number;
  y: number;
};

// a union of primitives (something an interface can't do)
type ID = string | number;

let userId: ID = 'abc-123';
let productId: ID = 42;

// tuples and function types
type Pair = [string, number];
type Callback = (err: Error | null) => void;

A type alias doesn't create a new type; it's just a new name for an existing one. ID and string | number are exactly the same thing.

10. type vs interface

Both can describe object shapes, and for most objects either works. The differences:

1. Extending

Interfaces use extends:

interface Animal {
  name: string;
}

interface Dog extends Animal {
  breed: string;
}

const myDog: Dog = { name: 'Buddy', breed: 'Labrador' };   // needs both fields

Type aliases have no extends keyword, but intersections (&) do the same job:

type Animal = { name: string };
type Dog = Animal & { breed: string };

Interfaces can also extend type aliases (interface Dog extends AnimalType {}), so the two mix freely.

2. Declaration merging

Declaring the same interface twice merges both into one:

interface Animal {
  name: string;
}
interface Animal {
  age: number;
}

const dog: Animal = { name: 'Buddy', age: 3 };   // must have both

Declaring the same type name twice is an error: ✗ Duplicate identifier 'Animal'.

Merging is useful for adding fields to library types (for example, adding a user property to Express's Request).

Comparison

Feature interface type
Object shapes ✓ ✓
Primitives, unions, tuples, functions ✗ ✓
Extend extends & (intersection)
Declaration merging ✓ ✗
Error messages Show the interface name Sometimes expand the full type
Typical use Object shapes, class contracts, public APIs Unions, intersections, utility-type results, function types
Rule of thumb

Use interface for object shapes and type for unions, intersections and everything else. The most important thing is to be consistent within a project.

11. Union and intersection types

Union (|): "one of these"

A union type accepts any one of several types:

type Status = 'pending' | 'approved' | 'rejected';

function setStatus(status: Status): void {
  console.log(`Status set to ${status}`);
}

setStatus('approved');   // ✓ editor autocompletes the three options
setStatus('done');
// ✗ Argument of type '"done"' is not assignable to parameter of type 'Status'.

Unions can mix any types, not just fixed values:

type Input = string | number | boolean;
You can only use what all members share

With value: string | number, you can't call value.toUpperCase() directly, because numbers don't have it. First narrow the type with a check like typeof value === 'string' (14. Type assertions and type guards).

Intersection (&): "all of these combined"

An intersection combines several types into one that has every property:

interface Colorful {
  color: string;
}
interface Circle {
  radius: number;
}

type ColorfulCircle = Colorful & Circle;

const myCircle: ColorfulCircle = {
  color: 'red',
  radius: 10,          // must have both
};
Union A | B Intersection A & B
Meaning Either A or B Both A and B
Value needs The fields of one member The fields of all members
Think of it as A choice A merge

Extra: intersecting incompatible primitives produces never: string & number is never, because no value can be both.

12. Literal types

A literal type is a type whose only allowed value is one exact value. Combined with unions, it lets you restrict a variable to a fixed set of options:

let direction: 'north' | 'south' | 'east' | 'west';

direction = 'north';   // ✓ editor suggests the four options
direction = 'up';
// ✗ Type '"up"' is not assignable to type '"north" | "south" | "east" | "west"'.

Numeric literals work the same way:

let diceRoll: 1 | 2 | 3 | 4 | 5 | 6;
diceRoll = 4;   // ✓
diceRoll = 7;   // ✗

Here the type is written directly on the variable. Usually you'd give it a name with type Direction = ... so you can reuse it.

Real use: modelling API responses (discriminated unions)

type SuccessResponse = {
  status: 'success';    // literal type acts as a "tag"
  data: string[];
};

type ErrorResponse = {
  status: 'error';
  message: string;
};

type ApiResponse = SuccessResponse | ErrorResponse;

function handle(res: ApiResponse) {
  if (res.status === 'success') {
    console.log(res.data);      // ✓ TypeScript knows this is SuccessResponse
  } else {
    console.log(res.message);   // ✓ and this is ErrorResponse
  }
}

The shared status field with a different literal value in each member is called a discriminant. Checking it tells TypeScript exactly which member you have. This pattern is very common for API responses, Redux actions and state machines.

as const (Extra)

as const makes TypeScript infer the narrowest possible literal types, and makes the value read-only:

const config = { mode: 'dark', size: 12 } as const;
// type: { readonly mode: "dark"; readonly size: 12 }

const ROLES = ['admin', 'user', 'guest'] as const;
type Role = typeof ROLES[number];   // "admin" | "user" | "guest"

13. Narrowing: the key idea

Before looking at assertions and guards, it helps to understand narrowing. When a value could be several types (a union, or unknown), TypeScript tracks your checks (if, switch, typeof, instanceof, ===) and narrows the type inside each branch:

function show(value: string | number) {
  // here: string | number
  if (typeof value === 'string') {
    // here: string
  } else {
    // here: number (the only option left)
  }
}

This is called control-flow analysis. Type guards (next section) are the checks that drive it.

14. Type assertions and type guards

Type assertions: "trust me, I know the type"

A type assertion tells TypeScript to treat a value as a specific type:

let someValue: unknown = 'Hello TypeScript';

let strLength: number = someValue.length;
// ✗ 'someValue' is of type 'unknown'.

let strLength1: number = (someValue as string).length;   // ✓ "as" syntax
let strLength2: number = (<string>someValue).length;     // ✓ angle-bracket syntax

After the assertion, autocomplete shows every string method.

Syntax Example Note
as value as string Preferred. Works everywhere.
Angle brackets <string>value Not allowed in .tsx files (it clashes with JSX).
Non-null ! (Extra) document.getElementById('app')! Asserts the value isn't null / undefined.
Assertions don't check anything

An assertion doesn't convert or verify the value; it just silences the compiler. If you're wrong, the bug appears at runtime:

const n: unknown = 42;
(n as string).toUpperCase();   // compiles, then crashes: toUpperCase is not a function

Prefer type guards, which actually check.

Type guards: checks that narrow the type

typeof guard: for primitives

function processValue(value: string | number) {
  if (typeof value === 'string') {
    console.log(value.toUpperCase());   // value: string → string methods
  } else {
    console.log(value.toFixed(2));      // value: number → number methods
  }
}

typeof can check for 'string', 'number', 'boolean', 'bigint', 'symbol', 'undefined', 'function' and 'object'.

Warning

typeof null === 'object' in JavaScript. Check value !== null too when testing for objects.

instanceof guard: for classes

class Dog {
  bark() { console.log('Woof'); }
}
class Cat {
  meow() { console.log('Meow'); }
}

function makeSound(animal: Dog | Cat) {
  if (animal instanceof Dog) {
    animal.bark();    // animal: Dog
  } else {
    animal.meow();    // animal: Cat
  }
}

instanceof checks whether an object was created by a class (or one that extends it). It doesn't work with interfaces or type aliases, because those don't exist at runtime.

in guard (Extra): checks whether a property exists

type Fish = { swim: () => void };
type Bird = { fly: () => void };

function move(pet: Fish | Bird) {
  if ('swim' in pet) pet.swim();   // pet: Fish
  else pet.fly();                  // pet: Bird
}

Custom type predicates (Extra)

Write your own guard function with a return type of value is Type:

interface User { name: string; email: string }

function isUser(value: unknown): value is User {
  return (
    typeof value === 'object' && value !== null &&
    'name' in value && 'email' in value
  );
}

const data: unknown = JSON.parse('{"name":"A","email":"a@x.com"}');
if (isUser(data)) {
  console.log(data.email);   // data: User
}

This is how you safely validate API responses at runtime. Libraries like Zod generate these checks for you.

Exhaustiveness checking with never (Extra)

Make TypeScript warn you when a new union member isn't handled:

type Shape = { kind: 'circle'; r: number } | { kind: 'square'; side: number };

function area(s: Shape): number {
  switch (s.kind) {
    case 'circle': return Math.PI * s.r ** 2;
    case 'square': return s.side ** 2;
    default: {
      const unreachable: never = s;   // ✗ error here if a new kind is added and not handled
      return unreachable;
    }
  }
}

Assertions vs guards

Type assertion Type guard
Checks at runtime? No Yes
Safe if you're wrong? No: runtime crash Yes: the branch just doesn't run
Use when You know more than the compiler (e.g. a DOM element you know exists) The type really varies at runtime

15. Classes

TypeScript classes are JavaScript classes plus property declarations, access modifiers and types.

Full form

class Person {
  private name: string;      // property declarations come first, with types
  protected age: number;
  public email: string;

  constructor(name: string, age: number, email: string) {
    this.name = name;
    this.age = age;
    this.email = email;
  }

  public introduce(): string {
    return `Hi, I'm ${this.name}`;
  }

  // getter: read like a property → person.userName
  get userName(): string {
    return this.name;
  }

  // setter: assign like a property → person.userName = 'X'
  set userName(value: string) {
    if (value.length === 0) throw new Error('Name required');
    this.name = value;
  }
}

const p = new Person('Alice', 27, 'p@x.com');
p.introduce();        // ✓ public
p.userName = 'Raj';   // ✓ goes through the setter
p.name;               // ✗ Property 'name' is private and only accessible within class 'Person'.
p.age;                // ✗ Property 'age' is protected and only accessible within class 'Person' and its subclasses.

Access modifiers

Modifier Accessible inside the class In subclasses Outside (on instances)
public (default) ✓ ✓ ✓
protected ✓ ✓ ✗
private ✓ ✗ ✗

Getters and setters let you keep a field private while still controlling how it's read and changed (for example, validating in the setter).

private vs #private (Extra)

TypeScript's private is checked only at compile time; the property still exists normally in the JavaScript output. JavaScript's own #name syntax is enforced at runtime too. Both work in TypeScript.

Short form: parameter properties

Adding a modifier to a constructor parameter declares and assigns the property automatically:

class Employee {
  constructor(
    private id: number,
    public name: string,
    protected department: string,
  ) {}                                  // empty body: assignment is automatic

  getDetails(): string {
    return `${this.name} works in ${this.department}`;
  }
}

const emp = new Employee(1, 'Alice', 'Engineering');
console.log(emp.getDetails());   // "Alice works in Engineering"

This is exactly equivalent to the full form, and much shorter. The compiled JavaScript is an ordinary class with this.id = id; and so on in the constructor.

readonly and static (Extra)

class Config {
  static version = '1.0';            // belongs to the class: Config.version
  readonly createdAt = new Date();   // can be set only in the declaration or constructor
}

implements: classes follow an interface (Extra)

interface Shape {
  area(): number;
}

class Square implements Shape {
  constructor(private side: number) {}
  area(): number { return this.side ** 2; }   // ✗ error if this method is missing
}

Abstract classes (Extra)

An abstract class can't be created directly; it's a base for other classes:

abstract class Animal {
  abstract makeSound(): string;            // subclasses must implement this
  move(): string { return 'Moving'; }      // shared implementation
}

class Dog extends Animal {
  makeSound(): string { return 'Woof'; }
}

// new Animal();  ✗ Cannot create an instance of an abstract class.

16. Inheritance

A class can extend another and reuse everything in it except private members:

class Manager extends Employee {
  constructor(
    id: number,
    name: string,
    department: string,
    private teamSize: number,      // new property only on Manager
  ) {
    super(id, name, department);   // call the parent (Employee) constructor first
  }

  getTeamInfo(): string {
    return `${this.name} manages ${this.teamSize} people in ${this.department}`;
    // ✓ name is public, department is protected; both are accessible here
    // ✗ this.id would fail: it's private to Employee
  }
}

const m = new Manager(2, 'Asha', 'Engineering', 8);
m.getDetails();    // inherited from Employee
m.getTeamInfo();   // own method

Key points:

  • extends creates the parent → child relationship.
  • super(...) calls the parent constructor. In a subclass constructor it must be called before using this.
  • Parameters without a modifier (id, name, department here) are plain parameters passed on to the parent, not new properties.
  • The subclass gets the parent's public and protected members, but not private ones.

Overriding methods (Extra)

class Manager extends Employee {
  override getDetails(): string {
    return `${super.getDetails()} (manager)`;   // call the parent version, then extend it
  }
}

The override keyword (with "noImplicitOverride": true in tsconfig) makes TypeScript error if the parent method doesn't exist, which catches typos and renames.

17. Generics

Generics are often considered the most confusing part of TypeScript. The core idea is simple: a generic is a type parameter, a placeholder for a type that's filled in when the code is used. Like a function parameter, but for types.

The problem generics solve

function identity(arg: any): any {
  return arg;
}

const output1 = identity('hello');   // type: any (we lost the info that it's a string)
const output2 = identity(42);        // type: any

The function clearly returns whatever it receives, but with any, TypeScript forgets the type.

Generic function

function identity<T>(arg: T): T {
  return arg;
}

const output1 = identity('hello');          // T inferred as string → output1: string
const output2 = identity(42);               // T inferred as number → output2: number
const output3 = identity<string>('hi');     // T set explicitly

How to read it:

  1. <T> right after the function name declares a type parameter named T.
  2. arg: T says "the argument has type T".
  3. : T says "the return value has the same type T".
  4. When called, TypeScript infers T from the argument, or you can pass it explicitly in angle brackets.

The name can be anything (<MyType> works), but single capital letters are the convention:

Name Usual meaning
T Type (the general one)
K Key
V Value
E Element
R Return type

Generic with arrays

function getFirstElement<T>(arr: T[]): T | undefined {
  return arr[0];
}

const firstNum = getFirstElement([1, 2, 3]);       // number | undefined
const firstStr = getFirstElement(['a', 'b']);      // string | undefined

The return type is T | undefined because an empty array has no first element. That's honest typing, and it forces callers to handle the empty case.

Generic interfaces

interface KeyValuePair<K, V> {
  key: K;
  value: V;
}

const stringNumberPair: KeyValuePair<string, number> = {
  key: 'age',
  value: 27,
};

const flagPair: KeyValuePair<string, boolean> = { key: 'isAdmin', value: true };

Generics can be nested inside more complex types:

interface Wrapper<K> {
  key: { name: string; myKey: K };
}

const w: Wrapper<string> = { key: { name: 'x', myKey: 'y' } };

Real-world example: a typed API response wrapper.

interface ApiResponse<T> {
  success: boolean;
  data: T;
}

const res: ApiResponse<User[]> = { success: true, data: [] };

Many libraries (React, Angular, Redux, Express types) use generics heavily. When you read their type definitions, you'll see <T>, <K, V> and constraints everywhere.

Generic classes

class DataStorage<T> {
  private data: T[] = [];

  addItem(item: T): void {
    this.data.push(item);
  }

  removeItem(item: T): void {
    this.data = this.data.filter((i) => i !== item);
  }

  getItems(): T[] {
    return [...this.data];
  }
}

const textStorage = new DataStorage<string>();
textStorage.addItem('Hello');
textStorage.addItem(42);
// ✗ Argument of type 'number' is not assignable to parameter of type 'string'.

const numberStorage = new DataStorage<number>();
numberStorage.addItem(42);   // ✓

One class definition gives you a type-safe store for any type.

Generic constraints (extends)

Sometimes T can't be just anything; it must have certain properties. Use extends to constrain it:

interface Lengthwise {
  length: number;
}

function logLength<T extends Lengthwise>(arg: T): T {
  console.log(arg.length);   // ✓ safe: every T is guaranteed to have .length
  return arg;
}

logLength('hello');      // ✓ strings have length
logLength([1, 2, 3]);    // ✓ arrays have length
logLength({ length: 5 });// ✓ any object with length
logLength(123);
// ✗ Argument of type 'number' is not assignable to parameter of type 'Lengthwise'.

Without the constraint, arg.length would be an error, because TypeScript can't assume an arbitrary T has a length.

keyof constraint (Extra)

function getProp<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { name: 'A', age: 30 };
getProp(user, 'name');    // string
getProp(user, 'age');     // number
getProp(user, 'email');   // ✗ "email" isn't a key of user
  • keyof T is the union of T's keys ('name' | 'age').
  • T[K] is the type of that property (an indexed access type).

Default type parameters (Extra)

interface Box<T = string> { value: T }

const a: Box = { value: 'hi' };          // T defaults to string
const b: Box<number> = { value: 1 };

18. Utility types

TypeScript ships with built-in generic types that transform other types, so you don't have to rewrite similar types by hand. Examples use this interface:

interface Todo {
  title: string;
  description: string;
  completed: boolean;
  createdAt: Date;
}

Partial<T>: make every property optional

type PartialTodo = Partial<Todo>;
// { title?: string; description?: string; completed?: boolean; createdAt?: Date }

const update: Todo = { completed: true };
// ✗ Type '{ completed: true; }' is missing the following properties from type 'Todo': title, description, createdAt

const update2: PartialTodo = { completed: true };   // ✓

Perfect for update functions, where callers send only the fields that changed:

function updateTodo(todo: Todo, changes: Partial<Todo>): Todo {
  return { ...todo, ...changes };
}

Required<T>: make every property required

The opposite of Partial. It removes every ?:

interface Settings {
  theme?: string;
  fontSize?: number;
}

type FullSettings = Required<Settings>;
// { theme: string; fontSize: number }

Readonly<T>: make every property read-only

const myTodo: Readonly<Todo> = {
  title: 'Learn TS',
  description: 'Utility types',
  completed: false,
  createdAt: new Date(),
};

myTodo.completed = true;
// ✗ Cannot assign to 'completed' because it is a read-only property.

Useful for state that must not be changed directly (configuration, Redux state).

Pick<T, Keys>: keep only some properties

type TodoPreview = Pick<Todo, 'title' | 'completed'>;
// { title: string; completed: boolean }

Omit<T, Keys>: remove some properties

type TodoWithoutDate = Omit<Todo, 'createdAt'>;
// { title: string; description: string; completed: boolean }

A common use: Omit<User, 'password'> for data you send to the client, or Omit<User, 'id'> for a create-user input before the database assigns an id.

Pick Omit
You list The keys to keep The keys to remove
Better when You need a few fields from a big type You need almost all fields

Record<Keys, Value>: build an object type from keys

type PageInfo = { title: string; url: string };
type Pages = 'home' | 'about' | 'contact';

type Merged = Record<Pages, PageInfo>;
// { home: PageInfo; about: PageInfo; contact: PageInfo }

const pages: Merged = {
  home:    { title: 'Home',    url: '/' },
  about:   { title: 'About',   url: '/about' },
  contact: { title: 'Contact', url: '/contact' },
};
  • Every key in the union becomes a required key; forgetting contact is an error.
  • Each value must match PageInfo, and autocomplete suggests title and url.
  • Record<string, number> is a quick way to type a dictionary.

ReturnType<typeof fn>: get a function's return type

function createUser() {
  return { id: 1, name: 'Alice', email: 'p@x.com' };
}

type UserType = ReturnType<typeof createUser>;
// { id: number; name: string; email: string }
  • typeof createUser (in a type position) gets the type of the function.
  • ReturnType<...> extracts what it returns.
  • Handy when a library returns a complex object but doesn't export its type. The type stays in sync automatically if the function changes.

More utility types (Extra)

Utility Does Example result
Parameters<typeof fn> Tuple of a function's parameter types Parameters<(a: string, b: number) => void> → [a: string, b: number]
Awaited<T> Unwraps a Promise Awaited<Promise<User>> → User
NonNullable<T> Removes null and undefined NonNullable<string | null> → string
Exclude<U, X> Removes members from a union Exclude<'a' | 'b' | 'c', 'a'> → 'b' | 'c'
Extract<U, X> Keeps only matching members Extract<'a' | 'b', 'a' | 'z'> → 'a'

Utility types combine: Partial<Pick<Todo, 'title' | 'description'>>.

How they work inside (Extra)

Utility types are written with mapped types, which loop over keys. Partial is essentially:

type MyPartial<T> = {
  [K in keyof T]?: T[K];   // for each key K of T, make it optional with the same type
};

19. Enums

An enum defines a named set of constants. A variable of that enum type can only hold one of those values.

Numeric enums

enum Direction {
  Up = 1,
  Down,     // 2
  Left,     // 3
  Right,    // 4
}

let dir: Direction = Direction.Right;   // value: 4
  • Members auto-increment from the previous value. Up = 1 is the initializer; the rest count up from it.
  • With Up = 8, Right becomes 11.
  • With no initializer at all, counting starts at 0.
  • Numeric enums also have reverse mapping: Direction[4] gives 'Right'.

String enums

enum Status {
  Pending = 'PENDING',
  Approved = 'APPROVED',
  Rejected = 'REJECTED',
}

let stat: Status = Status.Approved;
stat = 'APPROVED';
// ✗ Type '"APPROVED"' is not assignable to type 'Status'.
  • Every member needs an explicit string value (there's no auto-increment).
  • You must use Status.Approved, not the raw string. This keeps values consistent across the codebase.
  • String values are readable in logs and databases, which is why they're often preferred over numbers.

const enum

const enum HttpStatus {
  OK = 200,
  NotFound = 404,
  ServerError = 500,
}

function handleResponse(status: HttpStatus): void {
  if (status === HttpStatus.OK) console.log('Success');
  else if (status === HttpStatus.NotFound) console.log('Not found');
  else console.log('Server error');
}

handleResponse(HttpStatus.NotFound);

A normal enum compiles into a real JavaScript object. A const enum is removed entirely: each use is replaced with its literal value (HttpStatus.OK → 200). That makes the output smaller and slightly faster.

const enum caveat

const enum doesn't work well with build tools that compile one file at a time (Babel, esbuild, Vite, or isolatedModules: true). Many teams avoid it for that reason.

Enum vs union of literals (Extra)

// Enum
enum Role { Admin = 'admin', User = 'user' }

// Union of literals: zero runtime code
type RoleU = 'admin' | 'user';

// Object + as const: runtime values AND a type
const ROLE = { Admin: 'admin', User: 'user' } as const;
type RoleO = typeof ROLE[keyof typeof ROLE];   // 'admin' | 'user'
enum Union of literals as const object
Exists at runtime ✓ (object) ✗ ✓
Can loop over values ✓ ✗ ✓ (Object.values)
Accepts raw strings ('admin') ✗ ✓ ✓
Extra JS output Yes None Small

All three are valid. Unions are the lightest choice; enums are popular in backend code and for HTTP or status codes.

20. Promises and async/await

Typing a function that returns a Promise

Promise<T> is a built-in generic type: T is the type of the value the promise resolves with.

function fetchUser(id: number): Promise<{ id: number; name: string }> {
  return new Promise((resolve) => {
    setTimeout(() => resolve({ id, name: 'Alice' }), 1000);
  });
}

fetchUser(1).then((user) => {
  console.log(user.name);   // user: { id: number; name: string }
});

Using an interface keeps it readable:

interface User { id: number; name: string }

function fetchUser(id: number): Promise<User> { /* ... */ }

async functions

An async function always returns a Promise, so its return type is always Promise<...>:

async function getUserName(id: number): Promise<string> {
  const user = await fetchUser(id);   // await unwraps Promise<User> → User
  return user.name;                   // returns string → wrapped as Promise<string>
}

async function logUser(id: number): Promise<void> {
  const user = await fetchUser(id);
  console.log(user);                  // returns nothing → Promise<void>
}
Warning

Writing async function f(): string is an error: ✗ The return type of an async function or method must be the global Promise<T> type.

Generic fetch helper

async function fetchData<T>(url: string): Promise<T> {
  const response = await fetch(url);
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }
  return response.json() as Promise<T>;
}

interface Post { id: number; title: string }

const posts = await fetchData<Post[]>('https://jsonplaceholder.typicode.com/posts');
posts[0].title;   // ✓ typed as Post

The caller decides what T is, so one helper works for every endpoint.

The type is a promise, not a guarantee

as Promise<T> is a type assertion: TypeScript trusts you that the server returns Post[]. If the API changes, there's no error until runtime. For untrusted data, validate it with a type guard or a library like Zod (see 14. Type assertions and type guards).

Handling errors (Extra)

With strict on, the error in catch is unknown, because anything can be thrown:

try {
  await fetchData<Post[]>('/api/posts');
} catch (err) {
  // err: unknown
  if (err instanceof Error) {
    console.error(err.message);   // ✓ narrowed to Error
  } else {
    console.error('Unknown error', err);
  }
}

Running promises in parallel (Extra)

const [user, posts] = await Promise.all([
  fetchUser(1),                     // Promise<User>
  fetchData<Post[]>('/api/posts'),  // Promise<Post[]>
]);
// user: User, posts: Post[]  (TypeScript types each position of the tuple)

23. Self-check quiz

Why do we need to compile TypeScript?

Browsers and Node only run JavaScript. tsc checks the types, removes them, and outputs plain .js.

Do TypeScript types exist at runtime?

No. They're erased during compilation, so runtime data (API responses, input) still needs runtime checks.

What do rootDir and outDir do?

rootDir is where the .ts source lives (./src); outDir is where compiled .js goes (./dist).

Why keep strict: true?

It turns on checks like noImplicitAny and strictNullChecks. Without them TypeScript behaves almost like plain JavaScript.

Difference between an array and a tuple?

An array has any length with one element type (number[]). A tuple has a fixed length with a type per position ([string, number]).

Why is unknown safer than any?

You can't use an unknown value until you narrow it with a check; any lets you do anything unchecked.

What return type does a function with no return value have?

void.

What does let a = 'hi' infer vs const b = 'hi'?

a is string; b is the literal type "hi".

Where must optional parameters go?

After all required parameters.

What type does a rest parameter have?

An array type, e.g. ...nums: number[].

Name two differences between interface and type.

Interfaces use extends and support declaration merging; type can describe unions, primitives and tuples, and combines with &.

Union vs intersection?

A | B means either one (a value needs one member's fields); A & B means both combined (a value needs all fields).

What is a discriminated union?

A union of object types sharing a literal "tag" field (e.g. status: 'success' | 'error'). Checking the tag narrows to the exact member.

Does value as string convert the value to a string?

No. An assertion only changes what the compiler believes; nothing happens at runtime.

Which assertion syntax can't be used in .tsx files?

The angle-bracket form <string>value.

Which guard do you use for classes, and which for primitives?

instanceof for classes, typeof for primitives.

public vs protected vs private?

Public: accessible everywhere. Protected: inside the class and its subclasses. Private: only inside the class itself.

What does constructor(private id: number) {} do?

It declares a private id property and assigns the argument to it automatically (a parameter property).

What must a subclass constructor do before using this?

Call super(...).

Why use a generic instead of any?

A generic keeps the link between input and output types; any throws the type information away.

What does <T extends Lengthwise> do?

It constrains T to types that have a length: number property, so arg.length is safe.

Partial vs Required?

Partial<T> makes every property optional; Required<T> makes every property required.

Pick vs Omit?

Pick lists the keys to keep; Omit lists the keys to remove.

What does Record<'home' | 'about', PageInfo> produce?

{ home: PageInfo; about: PageInfo }, with both keys required.

How do you get the type a function returns?

ReturnType<typeof fn>.

In enum Direction { Up = 8, Down, Left, Right }, what is Right?

11. Members auto-increment from the initializer.

How is a const enum different from a normal enum?

It's removed at compile time and its uses are inlined as literal values, so no runtime object exists.

What's the return type of an async function that returns a string?

Promise<string>.

What is the type of err in catch (err) under strict mode?

unknown. Narrow it with err instanceof Error before reading .message.
