1. What is Rust?

Rust is a compiled, statically typed systems language focused on three things: speed, memory safety and fearless concurrency. It's used for command-line tools, web back ends, game engines, operating systems, blockchains and browsers.

The big idea

Languages manage memory in one of three ways:

Approach Examples Trade-off
Garbage collector (a background process cleans up unused memory) Java, JavaScript, Python, Go Safe and easy, but uses extra memory and occasionally pauses the program
Manual (you allocate and free memory yourself) C, C++ Fast and flexible, but easy to get wrong: leaks, crashes, security bugs
Ownership rules checked at compile time Rust As fast as C/C++, as safe as a garbage-collected language, but you must learn the rules

Rust's compiler refuses to build code that could cause memory bugs (dangling pointers, double frees, data races). The price is that it feels strict at first. This is often called "fighting the borrow checker", and nearly every Rust learner goes through it. Once your code compiles, a whole class of bugs simply can't exist.

How Rust compares

Rust JavaScript/Python Go C/C++
Compiled to machine code ✓ ✗ ✓ ✓
Garbage collector ✗ ✓ ✓ ✗
Memory-safety guaranteed by compiler ✓ ✓ (via GC) ✓ (via GC) ✗
Null values ✗ (uses Option) ✓ ✓ (nil) ✓
Exceptions ✗ (uses Result) ✓ ✗ ✓
Learning curve Steep Gentle Gentle Steep

4. Variables, types and functions

Variables and mutability

fn main() {
    let x = 5;          // immutable by default
    // x = 6;           // ✗ error: cannot assign twice to immutable variable `x`

    let mut y = 5;      // `mut` makes it changeable
    y = 6;
    println!("x = {x}, y = {y}");
}

Every variable is immutable unless you write mut. This is Rust's default for safety. (Section 12 explains why it matters.)

Printing

let name = "Alice";
let age = 30;
println!("Hello, {name}!");                 // inline variable
println!("{} is {} years old", name, age);  // positional
println!("{:?}", (1, 2));                   // Debug format (for types that support it)
println!("{:#?}", vec![1, 2]);              // pretty Debug
println!("{:.2}", 3.14159);                 // 3.14 (two decimals)
println!("{:>5}|{:<5}|{:^5}", 1, 2, 3);     // right, left, centre alignment

{} uses the Display format; {:?} uses the Debug format. Some types (like Vec) only support Debug.

Type annotations and inference

Rust infers most types, but you can write them:

let a: i32 = 10;
let b = 10;          // inferred as i32 (the default for integers)
let c = 3.5;         // inferred as f64 (the default for floats)
let d: u8 = 255;

Number types

Type Meaning Range
i8, i16, i32, i64, i128 Signed integers (positive and negative) i32: about ±2.1 billion
u8, u16, u32, u64, u128 Unsigned integers (zero and positive only) u32: 0 to about 4.29 billion
isize, usize Pointer-sized (64 bits on a 64-bit machine). usize is used for lengths and indexes
f32, f64 Floating-point (decimals). Default is f64
  • The number is the bits. More bits means bigger numbers and more memory.
  • Why unsigned? A signed number spends one bit on the sign, so an i32 holds half as many positive values as a u32. If a value can never be negative (an age, a count, an index), unsigned is the right type.
  • Overflow is caught: in debug builds, going past a type's limit panics (attempt to add with overflow).
let big: i32 = 2_147_483_647;   // underscores make numbers readable
// let too_big: i32 = 3_000_000_000;  // ✗ error: literal out of range for `i32`
let fine: i64 = 3_000_000_000;  // ✓

Other basic types

let is_ready: bool = true;

let text: &str = "hello";        // string slice, in DOUBLE quotes (section 19)
let nothing: () = ();            // the "unit" type: no value

Tuples and arrays

let person: (String, i32) = (String::from("Alice"), 30);
println!("{} is {}", person.0, person.1);
let (name, age) = person;           // destructuring

let nums: [i32; 3] = [1, 2, 3];     // array: fixed length, all the same type
println!("{} {}", nums[0], nums.len());
let zeros = [0; 5];                 // [0, 0, 0, 0, 0]

An array has a fixed size known at compile time. For a growable list use a vector (section 16).

Shadowing (Extra)

You can re-declare a variable with the same name; the new one shadows the old:

let spaces = "   ";
let spaces = spaces.len();   // now an integer: shadowing can change the type
println!("{spaces}");        // 3

This is different from mut: shadowing creates a new variable, so the type may change.

Constants (Extra)

const MAX_USERS: u32 = 100;   // always typed, always uppercase by convention

Functions

fn is_even(num: i32) -> bool {
    if num % 2 == 0 {
        return true;
    } else {
        return false;
    }
}

fn main() {
    let answer = is_even(10);
    println!("{answer}");          // true
    println!("{}", is_even(11));   // false
}

Expressions and implicit return

In Rust, the last expression in a block, written without a semicolon, is its value. So the function can be simplified:

fn is_even(num: i32) -> bool {
    num % 2 == 0          // no `return`, no semicolon → this value is returned
}
The semicolon matters

num % 2 == 0; (with a semicolon) turns the expression into a statement that produces (), and the compiler complains: mismatched types: expected bool, found (). Use return value; for early exits, and an unterminated final expression for the normal result.

if is also an expression:

let label = if is_even(4) { "even" } else { "odd" };

Loops

for i in 0..3 {            // 0, 1, 2   (end is exclusive)
    println!("{i}");
}
for i in 0..=3 { }         // 0, 1, 2, 3 (inclusive end)

let mut n = 3;
while n > 0 {
    n -= 1;
}

loop {                     // infinite loop; leave with `break`
    break;
}

Use _ for a loop variable you don't use: for _ in 0..5 { }. Without it you get an "unused variable" warning.

Example: Fibonacci

The Fibonacci sequence: 0, 1, 1, 2, 3, 5, 8, 13, … where each number is the sum of the two before it. Index 0 is 0, index 1 is 1, index 4 is 3.

fn fib(num: u32) -> u32 {
    let mut first = 0;
    let mut second = 1;

    if num == 0 {
        return first;
    }
    if num == 1 {
        return second;
    }

    for _ in 0..(num - 1) {
        let temp = second;
        second = second + first;
        first = temp;
    }
    second
}

fn main() {
    for i in 0..8 {
        println!("fib({i}) = {}", fib(i));
    }
}

Dry run for fib(4) (loop runs 3 times):

Iteration first second
start 0 1
1 1 1
2 1 2
3 2 3

Returns 3 ✓. Why mut? We reassign first and second. Why num - 1 iterations? We start already sitting at index 1, so we need num - 1 steps to reach index num.

Common mistake: off-by-one

Looping 0..(num - 2) returns the previous number. Always dry-run an algorithm on a tiny input before trusting it.

Example: string length

fn get_str_length(s: &str) -> usize {
    s.chars().count()
}

fn main() {
    let name = String::from("Alice");
    println!("{}", get_str_length(&name));   // 5
}
  • usize is the type of lengths.
  • chars() iterates over characters; count() counts them.
  • The & before name and &str as the parameter type are references (sections 15 and 19). For now, copy the pattern.
Practice: write fn max_of_three(a: i32, b: i32, c: i32) -> i32 
fn max_of_three(a: i32, b: i32, c: i32) -> i32 {
    let mut best = a;
    if b > best { best = b; }
    if c > best { best = c; }
    best
}

The standard library also has a.max(b).max(c).

Practice: write fn sum_to(n: u32) -> u32 that adds 1 through n 
fn sum_to(n: u32) -> u32 {
    let mut total = 0;
    for i in 1..=n {
        total += i;
    }
    total
}
// sum_to(10) == 55

5. Structs

A struct groups related values into one named type, like an object in JavaScript or a struct in C.

struct User {
    first_name: String,
    last_name: String,
    age: u32,
}

fn main() {
    let user = User {
        first_name: String::from("Alice"),
        last_name: String::from("Smith"),
        age: 32,
    };
    println!("{} {}", user.first_name, user.age);   // dot syntax reads fields
}
  • Define the shape once; then create as many values (instances) as you like.
  • Field order in the literal doesn't matter.
  • A struct instance must be mut to change a field: let mut user = ...; user.age = 33;.

Printing a whole struct

println!("{}", user);     // ✗ does NOT compile: `User` doesn't implement `std::fmt::Display`
println!("{:?}", user);   // ✗ does NOT compile: `User` doesn't implement `Debug`

println! doesn't know how to print your struct. The quick fix is to derive the Debug trait (traits are covered in section 21):

#[derive(Debug)]
struct User {
    first_name: String,
    last_name: String,
    age: u32,
}

fn main() {
    let user = User { first_name: "Alice".into(), last_name: "Smith".into(), age: 32 };
    println!("{:?}", user);    // User { first_name: "Alice", last_name: "Smith", age: 32 }
    println!("{:#?}", user);   // pretty, multi-line
}

("Alice".into() converts a &str into a String.)

"Unused field" warnings

Rust warns about fields you never read. That's a hint, not an error.

Methods: impl

You attach functions to a struct inside an impl block:

struct Rect {
    width: u32,
    height: u32,
}

impl Rect {
    // A method: first parameter is `&self`
    fn area(&self) -> u32 {
        self.width * self.height
    }

    fn perimeter(&self) -> u32 {
        2 * (self.width + self.height)
    }

    // A method with an extra argument
    fn scale(&self, factor: u32) -> Rect {
        Rect { width: self.width * factor, height: self.height * factor }
    }

    // An associated function: no `self`, called with `::`
    fn square(side: u32) -> Rect {
        Rect { width: side, height: side }
    }
}

fn main() {
    let r = Rect { width: 20, height: 10 };
    println!("area = {}", r.area());           // method call: dot
    println!("perimeter = {}", r.perimeter());
    let big = r.scale(2);
    println!("big area = {}", big.area());

    let sq = Rect::square(5);                   // associated function: ::
    println!("square area = {}", sq.area());
}
Kind First parameter How you call it Like in JavaScript
Method &self (or &mut self, or self) value.method() an instance method (this)
Associated function no self Type::function() a static method

self is the instance the method was called on (like this in a JS class). You don't pass it yourself: r.scale(2) passes r as self automatically, and 2 as factor.

Receiver Meaning
&self Borrow the struct to read it (most common)
&mut self Borrow it to change it
self Take ownership (consumes it; the caller can't use it afterwards) 
// A function without self cannot be called on an instance:
// r.square(5);        // ✗ error: no method named `square` found
Rect::square(5);       // ✓ call on the type
Convention

A constructor function is usually named new: fn new(width: u32, height: u32) -> Rect. It's just an ordinary associated function, not special syntax.

6. Enums and pattern matching

An enum is a type that can be exactly one of several variants. Use it whenever a value has a fixed set of possible kinds.

enum Direction {
    North,
    East,
    South,
    West,
}

fn move_around(dir: Direction) {
    // ... only four possible values ever arrive here
}

fn main() {
    let d = Direction::North;
    move_around(d);
}

Why not a string? With "North" someone could pass "Banana". With an enum the compiler guarantees only valid values exist, and the data is small and fast.

Variants can hold data

enum Shape {
    Circle(f64),             // radius
    Square(f64),             // side
    Rectangle(f64, f64),     // width, height
}

let c = Shape::Circle(2.0);
let r = Shape::Rectangle(3.0, 4.5);

(Literals like 2.0 must be written as floats for f64; 2 would be an integer.)

Reading the data: match

The match expression compares a value against patterns and runs the first one that fits:

use std::f64::consts::PI;

enum Shape {
    Circle(f64),
    Square(f64),
    Rectangle(f64, f64),
}

fn calculate_area(shape: &Shape) -> f64 {
    match shape {
        Shape::Circle(radius) => PI * radius * radius,
        Shape::Square(side) => side * side,
        Shape::Rectangle(width, height) => width * height,
    }
}

fn main() {
    println!("{:.2}", calculate_area(&Shape::Circle(2.0)));          // 12.57
    println!("{:.2}", calculate_area(&Shape::Square(3.0)));          // 9.00
    println!("{:.2}", calculate_area(&Shape::Rectangle(3.0, 4.5)));  // 13.50
}

Each arm is pattern => expression,. The values inside the variant are destructured into names (radius, side, …) that you can use on the right. Because match is an expression, the whole thing evaluates to a value and is returned.

match must be exhaustive

You must cover every variant. If you forget one, the compiler stops you:

error[E0004]: non-exhaustive patterns: `&Shape::Rectangle(_, _)` not covered

This is a safety net: add a new variant later and the compiler shows every place that needs updating. Use _ => ... as a catch-all if you really don't care about the rest.

let n = 3;
match n {
    1 => println!("one"),
    2 | 3 => println!("two or three"),     // several values
    4..=9 => println!("four to nine"),     // a range
    _ => println!("something else"),       // catch-all
}

if let: when you only care about one case (Extra)

let shape = Shape::Circle(1.5);
if let Shape::Circle(r) = shape {
    println!("a circle of radius {r}");
}

Methods on enums

Enums can have impl blocks, too:

impl Shape {
    fn area(&self) -> f64 {
        match self {
            Shape::Circle(r) => std::f64::consts::PI * r * r,
            Shape::Square(s) => s * s,
            Shape::Rectangle(w, h) => w * h,
        }
    }
}
Practice: add a Triangle(f64, f64) variant (base, height). What breaks?

Every match on Shape now fails to compile (non-exhaustive). Add the arm Shape::Triangle(b, h) => 0.5 * b * h, to fix it. That's the safety net in action.

7. Option: Rust's replacement for null

Many languages use null/undefined/nil for "no value", which causes the infamous null-pointer crashes. Rust has no null. Instead, the standard library provides an enum:

enum Option<T> {
    Some(T),   // there is a value
    None,      // there isn't
}

(<T> is a generic, explained in section 20: Option<i32> means "maybe an i32", Option<String> means "maybe a String".) Option, Some and None are available everywhere without importing.

The problem it solves

Write a function that returns the index of the first 'a' in a string. What do you return when there is no 'a'?

// Poor: -1 is a "magic number" and could be confused with a real result
fn find_first_a(s: &str) -> i32 { /* ... */ -1 }

The honest answer is "nothing", so return an Option:

fn find_first_a(s: &str) -> Option<usize> {
    for (i, c) in s.chars().enumerate() {
        if c == 'a' {
            return Some(i);
        }
    }
    None
}

fn main() {
    match find_first_a("banana") {
        Some(index) => println!("first 'a' is at index {index}"),
        None => println!("no 'a' found"),
    }
    match find_first_a("rust") {
        Some(index) => println!("first 'a' is at index {index}"),
        None => println!("no 'a' found"),
    }
}

Output: first 'a' is at index 1 then no 'a' found.

  • .enumerate() gives (index, item) pairs.
  • Some(i) wraps a value; None carries nothing.
  • The caller is forced to handle both cases with match. You can't "forget the null check", because you can't use the value without unwrapping it.
There's often a built-in

"banana".chars().position(|c| c == 'a') does the same thing and returns an Option<usize>. "banana".find('a') returns the byte index.

Handy Option methods (Extra)

let maybe: Option<i32> = Some(5);

maybe.unwrap();               // 5, but PANICS if it's None
maybe.expect("need a value"); // same, with your own panic message
maybe.unwrap_or(0);           // 5, or 0 if None (safe)
maybe.is_some();              // true
maybe.is_none();              // false
maybe.map(|n| n * 2);         // Some(10)  (None stays None)

if let Some(n) = maybe {      // handle just the Some case
    println!("{n}");
}
Practice: write fn first_even(nums: &[i32]) -> Option<i32> returning the first even number 
fn first_even(nums: &[i32]) -> Option<i32> {
    for &n in nums {
        if n % 2 == 0 {
            return Some(n);
        }
    }
    None
}
// first_even(&[1, 3, 4, 6]) == Some(4);  first_even(&[1, 3]) == None

8. Result: error handling

Where Option means "maybe a value", Result means "it worked, or here's what went wrong":

enum Result<T, E> {
    Ok(T),    // success, carrying the value
    Err(E),   // failure, carrying the error
}

Rust has no exceptions. A function that can fail returns a Result, and the caller decides what to do. It's part of the function's signature, so you can see at a glance that a function can fail.

Example: reading a file

use std::fs::read_to_string;

fn main() {
    let result = read_to_string("a.txt");   // Result<String, std::io::Error>

    match result {
        Ok(contents) => println!("File says: {contents}"),
        Err(error) => println!("Could not read the file: {error}"),
    }
}
  • use std::fs::read_to_string; imports a function from the standard library (functions in std aren't available until imported).
  • If a.txt doesn't exist, you get Err(...) instead of a crash.

Create a.txt next to Cargo.toml (run from the project folder) to see the Ok branch.

Don't swallow errors

// Poor: hides the failure
fn read_or_default(path: &str) -> String {
    match read_to_string(path) {
        Ok(data) => data,
        Err(_) => String::from("-1"),   // was the file missing, or does it contain "-1"?
    }
}

The caller can't tell a real result from a failure. Return the Result and let the caller decide:

use std::fs::read_to_string;
use std::io;

fn read_file(path: &str) -> Result<String, io::Error> {
    read_to_string(path)
}

fn main() {
    match read_file("a.txt") {
        Ok(data) => println!("{data}"),
        Err(e) => println!("error: {e}"),
    }
}

The ? operator (Extra, very common)

? means: "if this is Ok, give me the value; if it's Err, return that error from the current function immediately."

use std::fs::read_to_string;
use std::io;

fn count_lines(path: &str) -> Result<usize, io::Error> {
    let text = read_to_string(path)?;     // early-return on error
    Ok(text.lines().count())              // wrap the success value in Ok
}

fn main() {
    match count_lines("a.txt") {
        Ok(n) => println!("{n} lines"),
        Err(e) => println!("failed: {e}"),
    }
}

? only works in a function whose return type is Result (or Option). It replaces long chains of match.

unwrap, expect and panic!

let text = read_to_string("a.txt").unwrap();            // panics if Err
let text = read_to_string("a.txt").expect("no a.txt");  // panics with your message
panic!("something is badly wrong");                     // stop the thread right now

A panic stops the thread and prints thread 'main' panicked at src/main.rs:5:10. Use unwrap/expect for quick experiments and cases that truly can't fail; in real code, handle the error with match, ?, unwrap_or, etc.

Writing your own Result function

fn divide(a: f64, b: f64) -> Result<f64, String> {
    if b == 0.0 {
        return Err(String::from("cannot divide by zero"));
    }
    Ok(a / b)
}

fn main() {
    match divide(10.0, 2.0) {

10. Memory: stack vs heap

Everything from here to section 15 explains how Rust manages memory, which is the reason ownership rules exist.

What is memory?

When your program runs, its variables live in RAM. RAM is fast but limited (8–64 GB), compared with your SSD/hard drive. Every running program (your browser, your editor, your Rust program) uses some. Memory management means allocating (reserving) space when you need it and freeing it when you're done.

Two regions: the stack and the heap

Stack Heap
Size of data Known at compile time, fixed Not known until the program runs; can grow and shrink
Allocation Automatic, extremely fast (just move a pointer) Must ask the operating system for space; slower
Layout Last in, first out; one frame per function call A big pool of memory; items live anywhere
Freed Automatically when the function returns Must be cleaned up by someone (garbage collector, you, or Rust's ownership)
Typical data Numbers, booleans, chars, fixed arrays, structs of those String, Vec, HashMap, anything that can change size

The stack, step by step

fn find_sum(a: i32, b: i32) -> i32 {
    let answer = a + b;
    answer
}

fn main() {
    let x = 1;
    let y = 2;
    let z = find_sum(x, y);
    println!("{z}");
}
  1. main starts: a stack frame is pushed holding x, y, z (3 × 32 bits = 96 bits).
  2. find_sum is called: a new frame is pushed on top holding a, b, answer.
  3. find_sum returns: its frame is popped and its memory is instantly free.
  4. main finishes: its frame is popped. Done.

Numbers never change size (an i32 always uses 32 bits, whether it holds 1 or 1,000,000), so the stack handles them perfectly.

Why strings go on the heap

A String can grow:

let mut name = String::from("Alice");   // 5 characters now
name.push_str(" Smith");                // 11 characters later

The compiler can't know in advance how big it will become, so it can't reserve a fixed stack slot. So:

  • The characters live on the heap.
  • On the stack sits a small fixed-size value with three fields: a pointer to the heap data, the current length, and the capacity (how much heap space is reserved).
 STACK                         HEAP
┌───────────────┐            ┌───┬───┬───┬───┬───┐
│ name          │            │ A │ l │ i │ c │ e │
│  ptr ─────────┼──────────► └───┴───┴───┴───┴───┘
│  len = 5      │
│  cap = 5      │
└───────────────┘

When the string grows past its capacity, Rust asks for a bigger heap block, copies the data over, and updates the pointer. Vectors and hash maps work the same way.

The key insight

Heap data needs someone responsible for freeing it. How a language answers "who frees this, and when?" defines its memory model. Rust's answer is ownership (next sections).

11. Memory management in Rust vs C/C++ vs garbage-collected languages

The classic C++ bug: a memory leak

#include <iostream>
#include <cstring>

void create_string() {
    char* str = new char[30];                 // allocate 30 bytes on the heap
    std::strcpy(str, "hello from heap");
    std::cout << str << std::endl;
    // delete[] str;   // ← forgotten! The heap memory is never freed.
}

int main() {
    create_string();
    return 0;
}

When create_string ends, its stack frame (holding the pointer str) disappears, but the 30 heap bytes stay allocated with nothing pointing to them. That's a memory leak. In C and C++ the programmer must remember every free/delete; people forget, or free twice, or use memory after freeing it.

Common memory bugs

Bug What happens
Memory leak Heap memory is never freed; usage creeps up
Dangling pointer A pointer refers to memory that was already freed; using it is undefined behaviour
Double free The same memory is freed twice, which can corrupt the heap and is a security hole
Buffer overflow Writing past the end of an allocation
Data race Two threads change the same data at once without coordination

Rust's approach

The same program in Rust has no leak:

fn create_string() {
    let s = String::from("hello from heap");
    println!("{s}");
}   // ← `s` goes out of scope here and Rust frees its heap memory automatically

fn main() {
    create_string();
}

Rust inserts the clean-up call for you at the end of the scope (the drop). It does this at compile time, with no background garbage collector, so there's no pause and no extra overhead. The rules that make this safe are called ownership.

12. Mutability

By default every variable is immutable: once it has a value, it can't change.

fn main() {
    let name = String::from("hello");
    // name.push_str(" world");   // ✗ error[E0596]: cannot borrow `name` as mutable, as it is not declared as mutable

    let mut name2 = String::from("hello");
    name2.push_str(" world");     // ✓
    println!("{name2}");          // hello world
}

The same applies to numbers:

let a = 1;
// a = 2;       // ✗ error[E0384]: cannot assign twice to immutable variable `a`
let mut b = 1;
b = 2;          // ✓

Why immutable by default?

  • It tells readers: "this value never changes", which makes code easier to reason about.
  • It enables safe sharing: many parts of the code can read a value at once if nobody can change it (this becomes the borrowing rule in section 15).
  • It helps the compiler guarantee thread safety.

Add mut only where you really need change.

Mutability and the heap

A String is on the heap whether or not it's mut. mut doesn't affect where data lives; it only controls whether you're allowed to change it. Strings are always heap-allocated because they can grow, even if a particular string never does. The compiler doesn't try to prove "this one never changes".

13. Ownership

Ownership is Rust's central idea. It answers "who frees heap memory, and when?" without a garbage collector.

The three rules

  1. Each value has exactly one owner (a variable).
  2. There can only be one owner at a time.
  3. When the owner goes out of scope, the value is dropped (its memory is freed).
fn main() {
    {
        let s = String::from("hello");   // `s` owns the String
        println!("{s}");
    }   // `s` goes out of scope → the String is dropped and its heap memory freed
    // println!("{s}");   // ✗ error: cannot find value `s` in this scope
}

"Out of scope" means the closing } of the block where the variable was declared (a function body, an if, a loop, or a bare { } block).

Why only one owner?

If two variables owned the same heap data, both would try to free it when they went out of scope, giving a double free. If one freed it early while the other still pointed to it, you'd get a dangling pointer. A single owner rules out both bugs by construction.

It's similar to garbage collection... without the collector

A garbage collector periodically scans memory asking "does anything still point to this?". Rust answers the question at compile time: "the owner is leaving scope, so free it now". Result: deterministic clean-up, no pauses, no runtime cost.

Stack-only types are different

Simple types that live entirely on the stack (i32, bool, char, f64…) are copied instead of moved, because copying them is trivial. Ownership rules matter for heap-backed types like String and Vec (see Copy in the next section).

14. Moving values

What happens when you assign one variable to another?

fn main() {
    let s1 = String::from("hello");
    let s2 = s1;                 // ownership MOVES from s1 to s2
    println!("{s2}");            // ✓
    // println!("{s1}");         // ✗ error[E0382]: borrow of moved value: `s1`
}

You might expect a copy, or two pointers to the same data. Rust does neither. It moves ownership:

 before `let s2 = s1;`            after
 s1 ──► "hello" (heap)            s1 (now INVALID)
                                  s2 ──► "hello" (heap)

s1 becomes invalid, so there's still only one owner. When s2 goes out of scope, the memory is freed exactly once.

The compiler error tells you precisely what happened:

error[E0382]: borrow of moved value: `s1`
 |     let s1 = String::from("hello");
 |         -- move occurs because `s1` has type `String`, which does not implement the `Copy` trait
 |     let s2 = s1;
 |              -- value moved here
 |     println!("{s1}");
 |               ^^^^ value borrowed here after move
help: consider cloning the value if the performance cost is acceptable

Fix 1: clone()

If you really want two independent copies, ask for one explicitly:

fn main() {
    let s1 = String::from("hello");
    let s2 = s1.clone();         // a full copy on the heap
    println!("{s1} {s2}");       // both valid
}

clone() allocates new heap memory and copies the data. It's fine for learning and when you truly need a copy, but it costs time and memory, so prefer borrowing (next section) when you can.

A common beginner path

New Rustaceans often hit a move error and "just clone it". That's fine at first. The goal later is to restructure with references so you don't copy needlessly.

Passing to a function also moves

Passing a value as an argument is the same as let param = value;:

fn takes_ownership(s: String) {
    println!("{s}");
}   // `s` goes out of scope here → the String is dropped

fn main() {
    let name = String::from("Alice");
    takes_ownership(name);       // ownership moves INTO the function
    // println!("{name}");       // ✗ error[E0382]: borrow of moved value: `name`
}

Giving ownership back

A function can return the value to hand ownership back:

fn take_and_give_back(s: String) -> String {
    println!("{s}");
    s                             // returned: ownership moves back out
}

fn main() {
    let mut name = String::from("Alice");
    name = take_and_give_back(name);   // moved in, then moved back
    println!("{name}");                // ✓ valid again
}

This works but is clumsy. Borrowing (next section) is the better tool.

Copy types: no move

Types that live entirely on the stack are cheap to copy, so Rust copies them instead of moving:

fn main() {
    let a = 5;
    let b = a;                   // copied
    println!("{a} {b}");         // ✓ both valid
}

15. Borrowing and references

Moving ownership around is awkward. Usually a function just wants to look at a value, not own it. That's what references are for.

Shared references: &

fn print_string(s: &String) {      // takes a REFERENCE to a String
    println!("{s}");
}

fn main() {
    let name = String::from("Alice");
    print_string(&name);           // lend `name`; don't move it
    print_string(&name);           // ✓ still ours
    println!("{name}");            // ✓
}
  • &name creates a reference to name: a pointer that borrows the value.
  • &String in the parameter says "I take a reference to a String".
  • name stays the owner the whole time; the function only borrows it. No clone, no moving, no giving back.
  • The value is freed once, when name goes out of scope in main.
let s1 = String::from("hi");
let s2 = &s1;                      // s2 borrows s1
println!("{s1} {s2}");             // ✓ both valid

Compare with let s2 = s1; (a move) from section 14.

Mutable references: &mut

To change what you borrow, you need a mutable reference:

fn add_surname(s: &mut String) {
    s.push_str(" Smith");
}

fn main() {
    let mut name = String::from("Alice");   // 1. the variable must be `mut`
    add_surname(&mut name);                 // 2. lend it with `&mut`
    println!("{name}");                     // Alice Smith
}

Three things must line up: the variable is mut, you pass &mut value, and the parameter type is &mut T. Forget any one and the compiler tells you:

error[E0596]: cannot borrow `*s` as mutable, as it is behind a `&` reference

The borrowing rules

At any one time, you can have either:

  • any number of shared references (&T), or
  • exactly one mutable reference (&mut T),

but never both at once.

fn main() {
    let s = String::from("hi");
    let r1 = &s;
    let r2 = &s;                  // ✓ many readers are fine
    println!("{r1} {r2}");
}

fn main() {
    let mut s = String::from("hi");
    let r1 = &mut s;
    let r2 = &mut s;              // does NOT compile: second mutable borrow
    println!("{r1} {r2}");
}

error[E0499]: cannot borrow `s` as mutable more than once at a time

fn main() {
    let mut s = String::from("hi");
    let r1 = &s;                  // shared borrow
    let r2 = &mut s;              // does NOT compile: mutable borrow while shared exists
    println!("{r1} {r2}");
}

error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable

Why these rules?

It's the same idea as a database read/write lock:

  • Many readers at once are safe, because nobody is changing the data.
  • If someone is writing, nobody else may read or write; otherwise a reader could see half-changed data, or two writers could overwrite each other.

By enforcing this at compile time, Rust also prevents data races (section 23) and "iterator invalidation" bugs (changing a vector while looping over it).

References end at their last use (Extra)

A borrow lasts only until its last use, not until the end of the block. This is called non-lexical lifetimes, and it makes many programs that look conflicting compile fine:

fn main() {
    let mut s = String::from("hi");
    let r1 = &s;
    println!("{r1}");     // last use of r1
    let r2 = &mut s;      // ✓ OK: r1 is no longer used
    r2.push('!');
    println!("{r2}");
}

Dangling references are impossible

fn dangle() -> &String {              // does NOT compile
    let s = String::from("hi");
    &s                                // `s` is dropped at the end of the function...
}                                     // ...so this reference would point to freed memory

error[E0106]: missing lifetime specifier
  = help: this function's return type contains a borrowed value, but there is no value for it to be borrowed from

The fix is to return the owned value (s itself) instead. Section 22 (lifetimes) explains how Rust tracks this in general.

Mental model

Ownership = "who must clean this up". Borrowing = "using it temporarily without taking responsibility". & is a read-only loan; &mut is an exclusive, read-write loan.

16. Vectors

A Vec<T> is a growable list of values, all of type T. Like a dynamic array: you can push, pop and remove. Its data lives on the heap (section 10), with a small pointer-length-capacity record on the stack.

Creating and changing

fn main() {

    v.push(2);
    v.push(3);

Approach 2: change the original in place (mutable reference)

fn retain_even(v: &mut Vec<i32>) {
    let mut i = 0;
    while i < v.len() {
        if v[i] % 2 != 0 {
            v.remove(i);           // don't advance: the next item slid into index i
        } else {
            i += 1;
        }
    }
}

    retain_even(&mut v);
    println!("{:?}", v);           // [2, 4, 6]
}

17. HashMaps

A HashMap<K, V> stores key → value pairs with very fast lookup by key (like a JavaScript object/Map or a Python dict). Like vectors, the data lives on the heap.

use std::collections::HashMap;       // not in the prelude: must import

match users.get("alice") {
    Some(age) => println!("alice is {age}"),
    None => println!("user not found"),
}

The entry API: update or insert (Extra, very useful)

Count how many times each word appears:

use std::collections::HashMap;

fn main() {
    let text = "a b a c b a";
    let mut counts: HashMap<&str, i32> = HashMap::new();

    for word in text.split_whitespace() {
        *counts.entry(word).or_insert(0) += 1;
    }

    println!("{:?}", counts.get("a"));   // Some(3)
}

18. Iterators

An iterator produces a sequence of items one at a time. Every for loop you've written uses one behind the scenes. Iterators take over the fiddly work of walking through a collection's memory so you don't have to.

Iterators are lazy

Creating an iterator does nothing until something consumes it:

let v = vec![1, 2, 3];
let it = v.iter();     // nothing is processed yet

Three ways to iterate

Method Item type Effect on the vector Use when
v.iter() (or for x in &v) &T (shared reference) Borrowed; still usable afterwards; can't modify items Read-only passes (the usual case)
v.iter_mut() (or for x in &mut v) &mut T Borrowed mutably; items can be changed Modify items in place
v.into_iter() (or for x in v) T (owned) Consumed/moved; unusable afterwards You're done with the vector and want ownership of the items 
fn main() {
    let mut v = vec![1, 2, 3];

    for x in v.iter() {            // read-only
        println!("{x}");

    for x in v.iter_mut() {        // change in place
        *x += 10;                  // x is &mut i32 → dereference to modify
    }
    println!("{:?}", v);           // [11, 12, 13]

    for x in v {                   // consumes v (same as v.into_iter())
        println!("{x}");
    }
    // println!("{:?}", v);        // ✗ error[E0382]: borrow of moved value: `v`
}
A plain for x in v moves the vector

It's shorthand for v.into_iter(). If you need v afterwards, loop over &v (or v.iter()).

How iteration works: next()

Every iterator has a next() method that returns Some(item) until it's exhausted, then None. A for loop is just this:

fn main() {
    let v = vec![1, 2, 3];
    let mut it = v.iter();             // must be `mut`: next() advances it

    while let Some(x) = it.next() {    // loop until next() returns None
        println!("{x}");
    }
}

while let Some(x) = ... repeats while the pattern matches. You rarely write this by hand, but it's exactly what for does.

Adapters and consumers

Iterator methods come in two flavours:

Adapters Consumers
Return Another iterator (lazy) A final value
Examples map, filter, enumerate, take, skip, rev, zip sum, count, collect, min, max, fold, any, all
Effect on the iterator Wraps it Uses it up (takes ownership: you can't reuse it) 
fn main() {
    let v = vec![1, 2, 3];

    // map: transform each item
    let doubled: Vec<i32> = v.iter().map(|x| x * 2).collect();
    println!("{:?}", doubled);   // [2, 4, 6]

    // filter: keep items where the closure returns true
    let evens: Vec<&i32> = v.iter().filter(|x| *x % 2 == 0).collect();
    println!("{:?}", evens);     // [2]

    // sum: a consuming adapter
    let total: i32 = v.iter().sum();
    println!("{total}");         // 6
}
  • |x| x * 2 is a closure: an inline anonymous function (|parameters| body), like an arrow function in JavaScript.
  • collect() turns an iterator back into a collection. You must tell it which one (Vec<i32> here), because it can build many types.
  • sum() also needs a type annotation (let total: i32).

A consuming adapter uses the iterator up:

let v = vec![1, 2, 3];
let it = v.iter();
let total: i32 = it.sum();        // `sum` takes `self` by value → `it` is consumed
// let n = it.count();            // ✗ error[E0382]: use of moved value: `it`

(How do you know a method consumes? Its signature takes self, not &self.)

Chaining

fn main() {
    let v = vec![1, 2, 3, 4, 5];

    // keep the odd numbers, then double them
    let result: Vec<i32> = v
        .iter()
        .filter(|x| *x % 2 == 1)
        .map(|x| x * 2)
        .collect();

    println!("{:?}", result);   // [2, 6, 10]
}

Nothing happens until collect(): the pipeline processes one item at a time through every step.

Other useful pieces

let v = vec![10, 20, 30];

for (i, x) in v.iter().enumerate() { println!("{i}: {x}"); }   // index + item
let total: i32 = v.iter().map(|x| x / 10).sum();               // 6
let big = v.iter().any(|&x| x > 25);                           // true
let pos = v.iter().position(|&x| x == 20);                     // Some(1)
let rev: Vec<_> = v.iter().rev().collect();                    // [30, 20, 10]

Iterating a HashMap

use std::collections::HashMap;

fn main() {
    let mut scores = HashMap::new();
    scores.insert("blue", 10);
    scores.insert("red", 50);

    for (team, score) in &scores {      // borrow: `scores` stays valid
        println!("{team}: {score}");
    }
}

scores.iter() borrows; scores.into_iter() consumes, exactly as with vectors.

19. Strings vs string slices

Rust has two main string types, and the difference trips up almost everyone.

String &str (string slice)
Owns its data? Yes: it owns heap memory No: it's a borrowed view
Growable / mutable? Yes (if declared mut) No (read-only view)
Where the data lives Heap Anywhere: a String's heap data, or inside your program's binary (literals)
Size on the stack pointer + length + capacity pointer + length
Typical use Building and storing text Function parameters and literals

Both are UTF-8 encoded: they can hold any character from any language, not just English letters. (UTF-8 uses 1 to 4 bytes per character.)

String

fn main() {
    let mut name = String::from("Alice");   // or "Alice".to_string()
    println!("{name}");

    name.push_str(" Smith");                // append text
    name.push('!');                         // append one char
    println!("{name}");                     // Alice Smith!

    println!("{} bytes, {} chars", name.len(), name.chars().count());

    let mut s = String::from("Alice Smith");
    s.replace_range(5.., "");               // remove everything from byte 5 onward
    println!("{s}");                        // Alice
}

len() counts bytes, not characters. For "héllo" it's 6 bytes but 5 characters. Use chars().count() for the character count.

Other helpers: to_uppercase(), trim(), contains("x"), replace("a", "b"), split(','), and format!("{a}-{b}") to build a new String.

String slices: &str

A slice is a reference to a contiguous part of a string (or a vector/array). It borrows; it never owns.

fn main() {
    let word = String::from("hello world");

    let hello = &word[0..5];     // bytes 0..5 → "hello"  (start inclusive, end EXCLUSIVE)
    let world = &word[6..];      // from 6 to the end → "world"
    let all = &word[..];         // everything
    println!("{hello} {world} {all}");
}

Memory picture:

 STACK                        HEAP
 word:  ptr ──────────────►  h e l l o   w o r l d
        len = 11             ▲
 hello: ptr ─────────────────┘
        len = 5              (points at the same bytes, just 5 of them)

hello is a view into word's data: no copy and no new allocation.

Slice at character boundaries

Slice indexes are byte positions. Cutting in the middle of a multi-byte character panics: byte index 1 is not a char boundary. Safe for plain ASCII; be careful with non-English text.

String literals are &str

let greeting = "hello world";    // type: &str  (a slice pointing into the program's binary)

The text of every literal is baked into your compiled program. greeting is a borrowed view of that data, which lives for the whole run (&'static str, section 22). That's why you can't push to a literal: you only have a read-only view.

The key example: the first word of a string

Return a view of the first word instead of copying it:

fn first_word(s: &str) -> &str {
    for (i, c) in s.char_indices() {
        if c == ' ' {
            return &s[..i];     // view up to the first space
        }
    }
    s                            // no space → the whole string is one word
}

fn main() {
    let text = String::from("hello world");
    let word = first_word(&text);
    println!("{word}");          // hello
}

No new string is allocated: word points into text.

Now see why borrowing slices is safe:

fn main() {
    let mut text = String::from("hello world");
    let word = first_word(&text);   // `word` borrows `text` (shared)
    text.clear();                   // does NOT compile: needs a mutable borrow
    println!("{word}");
}

error[E0502]: cannot borrow `text` as mutable because it is also borrowed as immutable

clear() takes &mut self, but word (a shared borrow) is still in use afterwards. If this compiled, word would point at cleared memory: a dangling reference. Rust blocks it. A copy-based version (returning a new String) would silently go out of date instead; the slice version is both cheaper and safer.

Returning a reference to local data

fn first_word(s: String) -> &str {      // does NOT compile
    &s[..1]
}

s is owned by this function and dropped when it returns, so a reference into it would dangle. The compiler rejects it (missing lifetime specifier / cannot return reference to local variable). Fix: take a &str parameter, so the data belongs to the caller.

Which should I use in a function parameter?

fn count_vowels(s: &str) -> usize {          // ✓ accepts both!
    s.chars().filter(|c| "aeiou".contains(*c)).count()
}

fn main() {
    let owned = String::from("education");
    println!("{}", count_vowels("hello"));    // a &str literal
    println!("{}", count_vowels(&owned));     // a &String automatically becomes &str
}
Rule of thumb

Take &str for read-only text parameters (it accepts &String too, via deref coercion). Take String when the function needs to own the text (store it in a struct, return it). Return String from functions that build new text.

Slices work on arrays and vectors, too

fn main() {
    let arr = [1, 2, 3, 4, 5];
    let part: &[i32] = &arr[1..3];       // [2, 3]
    println!("{:?}", part);

    let v = vec![10, 20, 30, 40];
    let first_two = &v[..2];             // [10, 20]
    println!("{:?} {}", first_two, first_two.len());
}

&[T] is the slice type for "a view of some T values". The range is start..end with the end exclusive.

Type What it is
[i32; 3] array: owns exactly 3 integers (fixed size)
Vec<i32> vector: owns a growable list on the heap
&[i32] slice: borrows any run of integers
String / &str the same idea for text

20. Generics

Generics let one piece of code work for many types while staying fully type-checked (like generics in TypeScript, Java or C#).

The problem: repeated code

fn largest_i32(a: i32, b: i32) -> i32 { if a > b { a } else { b } }
fn largest_char(a: char, b: char) -> char { if a > b { a } else { b } }

Identical bodies, different types. Combine them with a type parameter T:

fn largest<T: PartialOrd>(a: T, b: T) -> T {
    if a > b { a } else { b }
}

fn main() {
    println!("{}", largest(3, 7));          // 7        (T = i32)
    println!("{}", largest('a', 'z'));      // z        (T = char)
    println!("{}", largest(1.5, 0.5));      // 1.5      (T = f64)
    println!("{}", largest("apple", "pear"));  // pear  (T = &str)
}
  • <T> after the function name declares a type parameter. Think of it as a variable that holds a type.
  • a: T, b: T means both arguments must be the same type, and the return type is that same type.
  • Rust works out T from your arguments.

Trait bounds: T: PartialOrd

a > b only makes sense for types that can be compared. A bare T could be anything (even something with no ordering), so the compiler needs a promise:

fn largest<T>(a: T, b: T) -> T {            // does NOT compile
    if a > b { a } else { b }
}

error[E0369]: binary operation `>` cannot be applied to type `T`
help: consider restricting type parameter `T` with trait `PartialOrd`

T: PartialOrd says "T may be any type, as long as it implements the PartialOrd trait (it supports <, >)". That's a trait bound (section 21). It's stricter than loosely-typed languages: calling largest with two structs that have no ordering is a compile error, instead of returning random results at runtime.

Different types: more parameters

fn pair<A, B>(first: A, second: B) -> (A, B) {
    (first, second)
}

let p = pair(1, "one");   // (i32, &str)

With one T, both arguments must match: largest(1, "x") is an error.

Generic structs and enums

struct Point<T> {
    x: T,
    y: T,
}

impl<T> Point<T> {
    fn x(&self) -> &T { &self.x }
}

fn main() {
    let int_point = Point { x: 1, y: 2 };          // Point<i32>
    let float_point = Point { x: 1.0, y: 2.5 };    // Point<f64>
    println!("{} {}", int_point.x(), float_point.x());
}

impl<T> Point<T> means "for every T, here are methods for Point<T>".

You've already been using generic types all along:

enum Option<T> { Some(T), None }          // "maybe a T"
enum Result<T, E> { Ok(T), Err(E) }       // "a T or an error E"
struct Vec<T> { /* ... */ }               // "a list of T"

That's what Vec<i32>, Option<usize> and Result<String, io::Error> mean: the type in the angle brackets fills in T. It's also why collect() needs a type: let v: Vec<i32> = ....

where clauses (Extra)

When bounds get long, move them:

use std::fmt::Display;

fn show_largest<T>(a: T, b: T) -> String
where
    T: PartialOrd + Display,
{
    if a > b { format!("{a}") } else { format!("{b}") }
}

Performance

Rust compiles a separate, specialised copy for each concrete type used (monomorphisation), so generic code is exactly as fast as hand-written code for each type. There's no runtime cost.

    items.first().cloned()
}

21. Traits

A trait defines shared behaviour: a set of methods that different types can implement. It's like an interface in TypeScript/Java (or an abstract class with no data).

Defining and implementing

trait Summary {
    fn summarize(&self) -> String;     // required: no body, implementors must provide it
}

struct User {
    name: String,
    age: u32,
}

struct Article {
    title: String,
}

impl Summary for User {
    fn summarize(&self) -> String {
        format!("User {} is {} years old", self.name, self.age)
    }
}

impl Summary for Article {
    fn summarize(&self) -> String {
        format!("Article: {}", self.title)
    }
}

fn main() {
    let u = User { name: String::from("Alice"), age: 30 };
    let a = Article { title: String::from("Learning Rust") };
    println!("{}", u.summarize());
    println!("{}", a.summarize());
}
  • trait Summary { ... } is the blueprint.
  • impl Summary for User says "User implements Summary". The compiler errors (not all trait items implemented, missing: summarize) if you forget a required method.
  • Different types give different implementations of the same method.

Default implementations

A trait can supply a default body; implementors may use it or override it:

trait Summary {
    fn summarize(&self) -> String {
        String::from("(read more...)")      // default
    }
}

struct Tweet;
struct User { name: String }

impl Summary for Tweet {}                    // empty impl: uses the default

impl Summary for User {                      // overrides it
    fn summarize(&self) -> String {
        format!("User {}", self.name)
    }
}

fn main() {
    println!("{}", Tweet.summarize());                                 // (read more...)
    println!("{}", User { name: String::from("Bob") }.summarize());    // User Bob
}

Traits as parameters

Accept any type that implements a trait:

fn notify(item: &impl Summary) {
    println!("Breaking news! {}", item.summarize());
}

Because item is guaranteed to implement Summary, you can call item.summarize(). Passing something that doesn't implement it is a compile error:

notify(&5);
// error[E0277]: the trait bound `{integer}: Summary` is not satisfied

You can implement your own traits for existing types, too:

impl Summary for String {
    fn summarize(&self) -> String {
        format!("String of {} bytes", self.len())
    }
}

(You may implement your own trait for any type, or any trait for your own type, but not a foreign trait for a foreign type. This is the "orphan rule".)

Trait bounds

&impl Summary is shorthand ("syntactic sugar") for the full trait bound form:

fn notify<T: Summary>(item: &T) {
    println!("Breaking news! {}", item.summarize());
}

This is the same generics syntax from section 20: T is generic, and : Summary restricts it.

Multiple bounds with +

trait Summary { fn summarize(&self) -> String { String::from("summary") } }
trait Describe { fn describe(&self) -> String { String::from("description") } }

struct User;
impl Summary for User {}
impl Describe for User {}

fn report<T: Summary + Describe>(item: &T) {
    println!("{} / {}", item.summarize(), item.describe());
}

fn main() {
    report(&User);     // ✓ User implements both
}

If User didn't implement Describe, you'd get the trait bound 'User: Describe' is not satisfied.

where clause and returning traits (Extra)

fn report<T>(item: &T)
where
    T: Summary + Describe,
{ /* ... */ }

fn make_summary() -> impl Summary {          // "returns some type that implements Summary"
    User
}

22. Lifetimes

The hardest topic

Lifetimes confuse almost everyone at first. You'll often be guided by compiler errors, so a second reading later is normal. The goal here is to understand what problem lifetimes solve; the syntax then makes sense.

The one-sentence idea

A lifetime is how long a reference stays valid. Rust uses lifetimes to guarantee a reference never outlives the data it points to (which would be a dangling reference).

The "longest" function

Start with a version that takes ownership, which compiles fine:

fn longest(a: String, b: String) -> String {
    if a.len() > b.len() { a } else { b }
}

fn main() {
    let s1 = String::from("small");
    let answer;
    {
        let s2 = String::from("longer");
        answer = longest(s1, s2);        // both are MOVED in; the winner moves out to `answer`
    }
    println!("{answer}");                // ✓ `answer` owns its data
}

Everything is owned, so there's nothing to dangle. Now switch to references (so we don't take ownership):

fn longest(a: &str, b: &str) -> &str {   // does NOT compile
    if a.len() > b.len() { a } else { b }
}

error[E0106]: missing lifetime specifier
 | fn longest(a: &str, b: &str) -> &str {
 |               ----     ----     ^ expected named lifetime parameter
 = help: this function's return type contains a borrowed value, but the signature does not say whether it is borrowed from `a` or `b`

Why the compiler complains

The function returns either a or b, depending on runtime data. The compiler can't know which, and so it can't know how long the returned reference stays valid. Imagine this caller:

// (uses the same `longest` as above)
fn main() {
    let s1 = String::from("small");
    let answer;
    {
        let s2 = String::from("longer");
        answer = longest(&s1, &s2);   // answer may point to s2...
    }                                 // ...but s2 is dropped here!
    println!("{answer}");             // would read freed memory → dangling reference
}

If s2 is the longer one, answer points at s2's data, which is freed at the inner }. The compiler wants you to describe the relationship so it can reject exactly this case.

Lifetime annotations

fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() > b.len() { a } else { b }
}
  • 'a (a tick followed by a name) is a lifetime parameter: a generic, declared in <...> just like <T>.
  • a: &'a str means "a is a reference that is valid for at least 'a".
  • -> &'a str means "the returned reference is valid for 'a too".

Reading it in plain English: "The returned reference lives no longer than the shorter-lived of the two inputs." 'a gets filled in as the overlap (intersection) of the regions where both a and b are valid.

Annotations don't change how long anything lives

They describe relationships to the compiler. 'a doesn't make s1 and s2 live equally long; it just says the result is only guaranteed valid where both inputs are.

Now the dangling example is correctly rejected:

fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() > b.len() { a } else { b }
}

fn main() {
    let s1 = String::from("small");
    let answer;
    {
        let s2 = String::from("longer");
        answer = longest(&s1, &s2);     // does NOT compile
    }
    println!("{answer}");
}

error[E0597]: `s2` does not live long enough
  |         answer = longest(&s1, &s2);
  |                                ^^^ borrowed value does not live long enough
  |     }
  |     - `s2` dropped here while still borrowed
  |     println!("{answer}");
  |               -------- borrow later used here

The compiler reasons: answer is valid only where both s1 and s2 are valid; s2 ends at the inner }, but you use answer after it. Even if s1 were the longer string in practice, the compiler can't know that, and it rejects the code to be safe.

The fix is to use the result inside the shorter scope (or keep both strings alive):

fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() > b.len() { a } else { b }
}

fn main() {
    let s1 = String::from("small");
    let s2 = String::from("longer");
    let answer = longest(&s1, &s2);
    println!("{answer}");               // ✓ both inputs outlive every use
}

Lifetimes in structs

A struct that holds a reference must say how long that reference lasts:

struct User<'a> {
    name: &'a str,
}

fn main() {
    let name = String::from("Alice");
    let user = User { name: &name };
    println!("{}", user.name);          // ✓
}

User<'a> means "a User can't outlive the string its name borrows". The compiler enforces it:

fn main() {
    let user;
    {
        let name = String::from("Alice");
        user = User { name: &name };    // does NOT compile
    }
    println!("{}", user.name);
}

error[E0597]: `name` does not live long enough

If your struct instead owns its data (name: String), no lifetime is needed. This is the simplest fix when lifetimes get annoying: own the data instead of borrowing it.

When do you need to write lifetimes?

Rarely, thanks to lifetime elision: the compiler fills them in for common patterns.

Situation Lifetimes needed?
One reference parameter, returning a reference (fn first(s: &str) -> &str) No: the output borrows from the single input automatically
A &self method returning a reference No: the output borrows from self
Two or more reference parameters and you return a reference (longest) Yes: the compiler can't guess which one you mean
A struct holding a reference Yes
A function that returns a reference with no reference input Impossible (it would dangle), except 'static

'static

'static is the longest lifetime: valid for the whole program. All string literals are &'static str:

let s: &'static str = "I live in the binary, forever";

Combining lifetimes, generics and traits

use std::fmt::Display;

fn longest_with_announcement<'a, T>(x: &'a str, y: &'a str, ann: T) -> &'a str
where
    T: Display,
{
    println!("Announcement! {ann}");
    if x.len() > y.len() { x } else { y }
}

fn main() {
    println!("{}", longest_with_announcement("abc", "de", "heads up"));
}

Lifetimes and type parameters share the angle brackets (lifetimes first). Here x and y are tied together by 'a; ann is any type that implements Display.

Practical advice

Follow the compiler's suggestions ("consider introducing a named lifetime parameter"). When a lifetime error feels impossible to fix, clone or own the data, or restructure so the data's owner lives in an outer scope. Understanding deepens with practice.

Practice: why does this fail, and how do you fix it? 
fn pick<'a>(a: &'a str, b: &str) -> &'a str {
    if a.len() > b.len() { a } else { b }
}

It fails because b has a different (unrelated) lifetime but is returned as &'a str. Either give b the same lifetime (b: &'a str), or only ever return a.

23. Threads

A thread is an independent flow of execution inside a program. Computers have several CPU cores; threads let you use more than one at the same time (parallelism). All the code so far ran on a single thread, so it used only one core, even though Rust supports many.

Spawning a thread

use std::thread;
use std::time::Duration;

fn main() {
    thread::spawn(|| {
        for i in 1..5 {
            println!("hi number {i} from the spawned thread");
            thread::sleep(Duration::from_millis(1));
        }
    });

    for i in 1..3 {
        println!("hi number {i} from the main thread");
        thread::sleep(Duration::from_millis(1));
    }
}
  • thread::spawn(closure) starts a new thread running the closure.
  • The output from the two threads interleaves, and the order can change each run.
  • When main ends, the whole program exits, even if spawned threads haven't finished, so the spawned thread's output may be cut off.

Waiting for a thread: join

spawn returns a JoinHandle. Call .join() to wait for that thread to finish:

use std::thread;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..5 {
            println!("spawned: {i}");
        }
    });

    handle.join().unwrap();      // wait here until the spawned thread is done

    for i in 1..3 {
        println!("main: {i}");   // runs only after the spawned thread finishes
    }
}

join() returns a Result (it's Err if the thread panicked), hence .unwrap().

Returning a value from a thread

use std::thread;

fn main() {
    let handle = thread::spawn(|| 2 + 2);
    let result = handle.join().unwrap();
    println!("{result}");        // 4
}

move closures

A thread can outlive the function that created it, so it can't just borrow variables from the surrounding scope: they might be freed first (a dangling reference). The compiler stops you:

use std::thread;

fn main() {
    let v = vec![1, 2, 3];
    let handle = thread::spawn(|| {              // does NOT compile
        println!("{:?}", v);
    });
    handle.join().unwrap();
}

error[E0373]: closure may outlive the current function, but it borrows `v`, which is owned by the current function
help: to force the closure to take ownership of `v`, use the `move` keyword

Add move so the closure takes ownership of the values it uses:

use std::thread;

fn main() {
    let v = vec![1, 2, 3];
    let handle = thread::spawn(move || {         // `v` is moved into the closure
        println!("{:?}", v);
    });
    handle.join().unwrap();
    // println!("{:?}", v);   // ✗ error[E0382]: borrow of moved value: `v`
}

This is ownership working as usual: v now belongs to the new thread.

Proving it uses multiple cores (try it!)

Run a CPU-heavy loop on the main thread and on one spawned thread, then watch CPU use in top/Activity Monitor/Task Manager. You'll see the process at about 200% (two cores). Add a second spawned thread and it climbs towards 300%. With no spawned threads, a Rust program stays near 100%.

use std::thread;

fn busy() {
    let mut c: u64 = 0;
    loop {
        c = c.wrapping_add(1);
        if c > 1_000 { c = 0; }
    }
}

fn main() {
    thread::spawn(busy);
    busy();                      // runs forever: press Ctrl+C to stop
}

Sharing data between threads (Extra)

To share mutable data safely you need two helpers:

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));   // Arc: shared ownership; Mutex: one-at-a-time access
    let mut handles = vec![];

    for _ in 0..4 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            for _ in 0..1000 {
                *counter.lock().unwrap() += 1;
            }
        }));
    }
    for h in handles {
        h.join().unwrap();
    }
    println!("{}", *counter.lock().unwrap());   // 4000
}
  • Arc (atomic reference counting) gives several owners safely across threads. (Plain ownership allows only one.)
  • Mutex lets one thread at a time change the data via lock().
Data races are impossible in safe Rust

The ownership and borrowing rules, extended by two traits (Send and Sync), mean Rust won't compile code that could race. The compiler is checking your concurrency, too.

Practice: spawn 3 threads that each print their number 
use std::thread;

fn main() {
    let mut handles = Vec::new();
    for id in 1..=3 {
        handles.push(thread::spawn(move || {
            println!("thread {id} says hi");
        }));
    }
    for h in handles {
        h.join().unwrap();
    }
}

24. Message passing with channels

Threads need to send results to each other. Rust's standard library provides channels for this ("share memory by communicating").

A channel has two halves:

Half Role
Transmitter (tx) Sends values into the channel
Receiver (rx) Takes values out of the channel

mpsc stands for multiple producer, single consumer: you can clone tx for many sending threads, but there's one receiver.

Basic send and receive

use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    thread::spawn(move || {
        let msg = String::from("hello from the spawned thread");
        tx.send(msg).unwrap();         // send moves `msg` into the channel
    });

    let received = rx.recv().unwrap(); // blocks until a message arrives
    println!("Got: {received}");
}
  • mpsc::channel() returns the (tx, rx) pair.
  • tx is moved into the thread (move).
  • tx.send(value) returns a Result (it fails if the receiver is gone). rx.recv() also returns a Result (it fails if all senders are gone and the channel is empty).
  • Sending moves the value: you can't use msg after send. That's ownership preventing two threads from touching the same data.

Handling the Results properly

match rx.recv() {
    Ok(value) => println!("got {value}"),
    Err(e) => println!("error while receiving: {e}"),
}

.unwrap() is fine in small examples; in real code, match on the Result so a failure doesn't crash the thread.

Receiving many messages

Treat rx like an iterator; the loop ends when every sender has been dropped:

use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    thread::spawn(move || {
        for i in 1..=3 {
            tx.send(i).unwrap();
        }
    });   // `tx` is dropped here, so the receiver loop will end

    for value in rx {
        println!("got {value}");
    }
}

Multiple producers: split a big job across threads

Sum the numbers 0 to 99,999,999 using 10 threads, each summing a 10-million-number slice, all sending partial results to one receiver:

use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    for i in 0..10u64 {
        let producer = tx.clone();                 // one producer per thread
        thread::spawn(move || {
            let start = i * 10_000_000;
            let end = (i + 1) * 10_000_000;        // exclusive
            let mut sum: u64 = 0;
            for n in start..end {
                sum += n;
            }
            producer.send(sum).unwrap();           // report this thread's partial sum
        });
    }

    drop(tx);                                      // IMPORTANT: drop the original sender

    let mut final_sum: u64 = 0;
    for partial in rx {                            // ends when ALL senders are dropped
        final_sum += partial;
    }
    println!("{final_sum}");                       // 4999999950000000
}

Check the maths: the sum of 0..N is N(N-1)/2; with N = 100,000,000 that's 4,999,999,950,000,000 ✓.

Points to understand:

Detail Why
u64 The total is far bigger than an i32/u32 can hold (otherwise: attempt to add with overflow panic)
tx.clone() Each thread gets its own sender (multiple producers)
move Each thread takes ownership of its producer
drop(tx) The original tx is never moved into a thread. While it's alive, the receiver keeps waiting for it, so for partial in rx never ends. Dropping it signals "no more senders from main"
0..10u64 Makes i a u64 so the arithmetic matches
The "program hangs forever" bug

If your receiver loop never finishes after all workers are done, you still have a live sender somewhere: forgetting drop(tx) is the classic cause.

Practice: send (thread_id, message) pairs from 3 threads and print them as they arrive

    let (tx, rx) = mpsc::channel();
    for id in 1..=3 {

25. Macros

A macro is code that writes other code at compile time. Anything ending in ! is a macro:

Macro What it expands to
println!("x = {x}") Code that formats and prints
vec![1, 2, 3] Code that creates a Vec and pushes three items
format!("{a}-{b}") Code that builds a String
panic!("boom") Code that stops the thread with a message
assert_eq!(a, b) A test that panics if a != b

Why macros instead of functions? A function takes a fixed number of typed arguments; a macro can take any number of arguments (println!("{} {}", a, b)) and generate code from them.

A tiny custom macro (Extra)

macro_rules! say_hello {
    () => {
        println!("Hello!");
    };
}

macro_rules! square {
    ($x:expr) => {
        $x * $x
    };
}

fn main() {
    say_hello!();
    println!("{}", square!(2 + 3));   // 25
}

macro_rules! matches patterns of code and substitutes them into templates. ($x:expr captures any expression.) Writing complex macros requires understanding how a compiler parses code (syntax trees), so most developers use macros far more than they write them. Start by using macros confidently.

29. Self-check quiz

What makes Rust memory-safe without a garbage collector?

Compile-time ownership rules: each value has one owner; when the owner leaves scope the value is dropped. Borrowing rules prevent dangling references and data races.

What's the difference between binary and library crates?

A binary (src/main.rs) builds an executable with a main function. A library (src/lib.rs) is reusable code other crates depend on.

Why are variables immutable by default?

It makes code easier to reason about and enables safe sharing; you opt in to change with mut.

What does an i32 vs a u32 differ in?

i32 is signed (negative and positive, roughly ±2.1 billion); u32 is unsigned (0 to roughly 4.29 billion).

What does the last expression without a semicolon do?

It becomes the value of the block/function (implicit return). Adding ; turns it into a statement returning ().

What's the difference between a method and an associated function?

A method takes self (&self, &mut self, self) and is called with value.method(). An associated function has no self and is called with Type::function().

Why use an enum instead of a string for a fixed set of options?

The compiler guarantees only valid variants exist, it's smaller and faster, and match forces you to handle every case.

What does match require?

Every possible case must be handled (exhaustiveness); use _ as a catch-all.

Why does Rust have Option instead of null?

It makes "might be missing" part of the type, so you're forced to handle the missing case and can't forget a null check.

Why does Rust have Result instead of exceptions?

Errors are ordinary return values visible in the function signature, and the caller chooses how to handle them (match, ?, unwrap_or).

What does the ? operator do?

On Ok(v) it yields v; on Err(e) it returns that error from the current function immediately.

What's stored on the stack vs the heap for a String?

The stack holds a pointer, length and capacity; the characters live on the heap, because the size can change at runtime.

State the three ownership rules.

Each value has an owner; there's only one owner at a time; when the owner goes out of scope the value is dropped.

Why does let s2 = s1; invalidate s1 for a String?

Ownership moves to s2. Two owners would lead to a double free, so s1 can no longer be used. (Integers are Copy, so they aren't moved.)

What does passing a String to a function do?

It moves ownership into the function, which drops it at the end, unless you pass a reference (&) or return it.

What are the borrowing rules?

Any number of & shared references or exactly one &mut; never both at once. References must always be valid.

What does the mut keyword need on each of three places to pass a mutable reference?

The variable is let mut, the call passes &mut value, and the parameter type is &mut T.

What does v[10] do on a 3-item vector? What about v.get(10)?

v[10] panics; v.get(10) returns None.

iter() vs iter_mut() vs into_iter()?

iter yields &T (read-only borrow); iter_mut yields &mut T (can modify); into_iter yields T and consumes the collection. A plain for x in v uses into_iter.

Adapter vs consumer?

An adapter (map, filter) returns another lazy iterator. A consumer (sum, collect, count) uses the iterator up and produces a value.

Why does collect() need a type?

It can build many collection types, so it needs to know which one (Vec<i32>, HashMap, String…).

String vs &str?

String owns growable heap text. &str is a borrowed view of text stored elsewhere (including literals). Prefer &str for read-only parameters.

Why does s.clear() fail while a first_word(&s) result is alive?

The slice holds a shared borrow of s; clear needs &mut s. Rust forbids it so the slice can't dangle.

What does T: PartialOrd mean?

T can be any type that implements PartialOrd (supports <, >). It's a trait bound on a generic.

What does impl Trait for Type do, and what if you omit a required method?

It declares that Type implements the trait. A missing required method is a compile error.

What is #[derive(Debug)]?

A shortcut that auto-generates a Debug implementation so {:?} works.

Why does longest(a: &str, b: &str) -> &str need lifetimes?

The function returns one of two references, so the compiler needs to be told the result is valid only as long as both inputs: fn longest<'a>(a: &'a str, b: &'a str) -> &'a str.

Do lifetime annotations change how long values live?

No. They only describe relationships so the compiler can verify references never outlive their data.

Why does a struct holding a &str need <'a>?

The struct can't outlive the string it borrows, and the lifetime parameter expresses that.

What does thread::spawn return and how do you wait for the thread?

A JoinHandle; call .join() (which returns a Result).

Why is move needed on thread closures?

The thread may outlive the current scope, so the closure must own the values it uses rather than borrow them.

What does mpsc stand for and why drop(tx)?

Multiple producer, single consumer. The original sender must be dropped, or the receiver loop never sees "all senders gone" and hangs.

What is a macro, and how can you tell one apart from a function?

Code that generates code at compile time; macro names end with ! (println!, vec!).
