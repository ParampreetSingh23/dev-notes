1. What is Fastify?

Fastify is a web framework for Node.js. A web framework handles the low-level HTTP work for you (parsing requests, matching URLs to code, sending responses), so you only write your app's logic.

The official tagline is "Fast and low overhead web framework for Node.js". "Low overhead" means the framework adds very little extra work on top of Node's own HTTP server.

How fast?

Framework Requests / second (benchmark shown in video)
Fastify ~45,000
Express ~9,900

That is roughly 4–5× more requests on the same machine. The benchmark page is on the Fastify website (fastify.dev → Benchmarks).

Why is it fast?

Reason What it means
Fast router Fastify uses find-my-way, a radix-tree router, so matching a URL to a route is very quick even with many routes.
Schema-based serialization If you give a response schema, Fastify uses fast-json-stringify to build JSON much faster than JSON.stringify.
Compiled validation Request schemas are compiled once (with Ajv) into fast validation functions at startup.
Fast logger The built-in logger is pino, one of the fastest Node.js loggers.
Encapsulated plugins Plugins keep code isolated, so the framework does less work per request.

When to choose Fastify

  • You want an Express-like API but better performance.
  • You want built-in validation and logging instead of adding extra libraries.
  • You are building JSON APIs or microservices (like our auth service).

Key terms used in these notes

Term Meaning
Instance The fastify object you create. Routes, plugins and hooks are added to it.
Route A method + URL pair (e.g. GET /api/users) linked to a function.
Handler The function that runs for a route and produces the response.
Plugin A function that adds routes, hooks or features to an instance.
Hook A function that runs at a specific stage of a request's life (like Express middleware).
Schema A JSON description of what data should look like, used to validate input and shape output.
Serialization Turning a JavaScript object into a JSON string to send to the client.

2. Project setup

Prerequisites

  • Node.js 20+ (the video uses Node 22). Check with node -v.
  • npm (comes with Node).
  • A code editor, Postman (to send test requests), and MongoDB (used later).

Create the project

mkdir auth-service
cd auth-service
npm init -y
npm install fastify

What each command does:

Command Effect
mkdir auth-service Creates the project folder. We are pretending to build an authentication service.
npm init -y Creates package.json with default values (-y answers "yes" to every question).
npm install fastify Downloads Fastify into node_modules/ and adds it to dependencies in package.json.

The installation guide is in the docs at fastify.dev → Docs → Guides → Getting Started. You can also use yarn add fastify.

Enable ES modules

Node supports two module systems:

CommonJS (old default) ES Modules (modern)
Import const Fastify = require('fastify') import Fastify from 'fastify'
Export module.exports = fn export default fn
How to enable Default "type": "module" in package.json

The video uses ES modules, so add this to package.json:

{
  "name": "auth-service",
  "type": "module",
  "dependencies": {
    "fastify": "^5.0.0"
  }
}
ESM needs file extensions

With ES modules, local imports must include the .js extension: import userRouter from './src/routes/user.js'. Without .js, Node throws ERR_MODULE_NOT_FOUND.

3. Creating the server

Create server.js in the project root.

// server.js
import Fastify from 'fastify';

// 1. Create the instance
const fastify = Fastify({ logger: true });

// 2. Choose the port
const PORT = Number(process.env.PORT) || 4000;

// 3. Start the server
const start = async () => {
  try {
    await fastify.listen({ port: PORT });
    console.log(`Server listening on port ${PORT}`);
  } catch (err) {
    fastify.log.error(err);
    process.exit(1);
  }
};

start();

Line-by-line explanation

  1. import Fastify from 'fastify': loads the framework. Fastify is a factory function.
  2. Fastify({ logger: true }): creates a new app instance. The options object configures it. logger: true turns on the built-in pino logger, so every request is logged as structured JSON.
  3. process.env.PORT || 4000: uses the PORT environment variable if one is set (for example on a hosting platform), otherwise 4000.
  4. fastify.listen({ port }): starts the HTTP server. It returns a promise, so we await it inside an async function.
  5. try / catch: if the server can't start (for example, the port is already in use), we log the error with fastify.log.error and stop the process with process.exit(1). Exit code 1 means "failed".

listen() also accepts a callback (fastify.listen({ port }, (err, address) => {...})), but async/await is cleaner.

What you see in the terminal

{"level":30,"time":1730000000000,"pid":1234,"hostname":"mac","msg":"Server listening at http://[::1]:4000"}
{"level":30,"time":1730000000000,"pid":1234,"hostname":"mac","msg":"Server listening at http://127.0.0.1:4000"}
  • Two lines appear because localhost resolves to both IPv6 ([::1]) and IPv4 (127.0.0.1), and Fastify listens on both.
  • level: 30 means "info". Pino levels: 10 trace, 20 debug, 30 info, 40 warn, 50 error, 60 fatal.

Opening http://localhost:4000 in the browser returns:

{ "message": "Route GET:/ not found", "error": "Not Found", "statusCode": 404 }

That's expected: we haven't declared any routes yet. Fastify sends a JSON 404 automatically.

Useful options (Beyond the video)

const fastify = Fastify({
  logger: {
    level: 'info',
    transport: { target: 'pino-pretty' }, // readable, coloured logs in development (npm i -D pino-pretty)
  },
});

await fastify.listen({
  port: PORT,
  host: '0.0.0.0', // listen on all network interfaces: needed inside Docker or on a server
});
Docker gotcha

The default host is localhost, which only accepts connections from the same machine. Inside a Docker container you must use host: '0.0.0.0', or the app can't be reached from outside the container.

4. Dev workflow: nodemon and .env

nodemon

Without a tool, you have to stop and restart the server after every code change. nodemon watches your files and restarts automatically.

npm install -D nodemon

-D (same as --save-dev) puts it in devDependencies. These are tools needed only while developing, not in production.

{
  "type": "module",
  "scripts": {
    "dev": "nodemon server.js"
  },
  "dependencies": { "fastify": "^5.0.0" },
  "devDependencies": { "nodemon": "^3.1.0" }
}

npm run dev

Environment variables with .env

Secrets and settings that change between machines (database URL, port, JWT secret) belong in a .env file, not in code:

# .env
PORT=4000
DB_URL=mongodb://localhost:27017/fastify-auth-service

Node 20.6+ (and Node 22, used in the video) can read .env files natively with the --env-file flag, so you don't need the dotenv package:

"scripts": {
  "dev": "nodemon --exec \"node --env-file=.env\" server.js"
}

Alternative with no nodemon at all, using Node's built-in watch mode:

"scripts": {
  "dev": "node --watch --env-file=.env server.js"
}
Never commit .env

Add .env to .gitignore. It contains secrets. Commit a .env.example with dummy values instead, so teammates know which variables to set.

5. Routes & handlers

A route connects an HTTP method + URL to a handler function.

Shorthand methods

fastify.get('/', async (request, reply) => {
  return { message: 'Welcome to auth service' };
});
Method Typical use
fastify.get(url, handler) Read data
fastify.post(url, handler) Create data
fastify.put(url, handler) Replace a whole resource
fastify.patch(url, handler) Update part of a resource
fastify.delete(url, handler) Delete data

All of them accept an optional options object as the second argument (fastify.post(url, options, handler)). That's where schemas and route-level hooks go (sections 7, 8 and 15).

Full declaration (Beyond the video)

The shorthand methods are sugar for fastify.route():

fastify.route({
  method: 'GET',
  url: '/',
  schema: { /* ... */ },
  preHandler: someHook,
  handler: async (request, reply) => ({ message: 'Welcome' }),
});

request and reply

The handler receives two objects, the same idea as req and res in Express. By convention Fastify calls the second one reply.

Useful request properties:

Property Contains
request.body Parsed JSON body (POST/PUT/PATCH)
request.query Query string as an object (?q=john → { q: 'john' })
request.params URL params (/users/:id → { id: '...' })
request.headers Request headers (lowercase keys, e.g. authorization)
request.method / request.url HTTP method and URL
request.ip Client IP address
request.id Unique request id (also shown in logs)
request.log Logger bound to this request (log lines include the request id)

Useful reply methods:

Method Does
reply.code(201) / reply.status(201) Set the status code
reply.send(data) Send the response
reply.header('key', 'value') Set a response header
reply.type('text/html') Set Content-Type
reply.redirect('/login') Redirect

Returning vs reply.send()

In an async handler you can just return a value. Fastify serializes it to JSON and sends it, so you don't need reply.send():

// Option 1: return (preferred in async handlers)
fastify.get('/a', async (request, reply) => {
  return { ok: true };
});

// Option 2: reply.send
fastify.get('/b', (request, reply) => {
  reply.send({ ok: true });
});
Don't mix both

In an async handler, use either return data or return reply.send(data). If you call reply.send() and also return a value, Fastify logs a Reply was already sent error.

6. Plugins: organising your code

Key idea

"In JavaScript everything is an object; in Fastify everything is a plugin." Routes, database connections, hooks and decorators are all added with fastify.register().

Why plugins?

Putting every route in server.js quickly becomes messy. Plugins let you split code into files by feature (users, auth, uploads), much like express.Router(), but with more power (isolation, options, prefixes).

What a plugin looks like

A plugin is a function that receives:

  1. fastify: an instance you can add routes or hooks to.
  2. options: whatever you passed to register().

Folder structure for our project:

auth-service/
├── package.json
├── server.js            # creates app, registers plugins, starts server
├── .env
├── static/              # uploaded files land here
└── src/
    ├── routes/
    │   └── user.js      # user routes plugin
    └── hooks/
        └── auth.js      # auth hook (middleware)

// src/routes/user.js
async function userRouter(fastify, options) {
  fastify.post('/api/users', async (request, reply) => {
    return { message: 'User created' };
  });
}

export default userRouter;

// server.js
import userRouter from './src/routes/user.js';

fastify.register(userRouter);

Testing in Postman

  1. Create a collection named "Auth Service".
  2. Add a request named Create User, method POST, URL http://localhost:4000/api/users.
  3. Click Send and you should get { "message": "User created" }.

Register options: prefix (Beyond the video)

Instead of writing /api/users in every route, pass a prefix:

fastify.register(userRouter, { prefix: '/api/users' });

// inside userRouter:
fastify.post('/', handler);     // → POST /api/users
fastify.get('/:id', handler);   // → GET  /api/users/:id

Encapsulation: plugins are isolated (Beyond the video)

Each registered plugin gets its own child context. Anything added inside a plugin (hooks, decorators, other plugins) is visible only inside that plugin and its children, not to its parent or siblings.

root instance (server.js)
├── userRouter plugin      ← hooks added here affect only user routes
└── uploadRouter plugin    ← can't see userRouter's hooks

That's why section 15 can apply a hook "only to user routes".

To share something with the whole app (for example a database connection), wrap the plugin with fastify-plugin, which removes the isolation:

import fp from 'fastify-plugin';

export default fp(async function dbPlugin(fastify) {
  fastify.decorate('db', someConnection); // now fastify.db works everywhere
});
Note

Official plugins like @fastify/mongodb are already wrapped with fastify-plugin. That's why fastify.mongo registered in server.js is available inside the user routes plugin.

Decorators (Beyond the video)

A decorator adds a custom property or method to the instance, request or reply:

fastify.decorate('config', { appName: 'auth' });  // fastify.config
fastify.decorateRequest('userId', null);           // request.userId (set later in a hook)
fastify.decorateReply('ok', function (data) {      // reply.ok(data)
  return this.code(200).send({ success: true, data });
});

7. Request validation (JSON Schema)

Why validate?

Never trust client input. Without validation, a client could send a missing email, a number instead of a string, or a huge payload, and your code or database would break. Validation rejects bad requests before your handler runs.

Fastify has validation built in using JSON Schema (powered by the Ajv library). You don't need Joi, Zod, or any other library.

JSON Schema basics

JSON Schema is a standard way to describe the shape of JSON data.

Keyword Example Meaning
type 'string', 'number', 'integer', 'boolean', 'object', 'array' Data type
properties { name: { type: 'string' } } Fields of an object
required ['name', 'email'] Fields that must be present
minLength / maxLength { type: 'string', minLength: 8 } String length
minimum / maximum { type: 'number', minimum: 18 } Number range
format { type: 'string', format: 'email' } Built-in formats: email, uri, date, date-time, …
pattern { type: 'string', pattern: '^[a-z]+{{BODY}}#39; } Regex the string must match
enum { enum: ['user', 'admin'] } Allowed values
items { type: 'array', items: { type: 'string' } } Type of array elements
additionalProperties false Reject or strip fields not listed in properties
default { type: 'integer', default: 10 } Value used if the field is missing

The schema from the video

The body we send from Postman (Body → raw → JSON):

{
  "name": "Coder",
  "email": "coder@example.com",
  "password": "password"
}

const createUserSchema = {
  body: {
    type: 'object',
    required: ['name', 'email', 'password'],
    properties: {
      name:     { type: 'string' },
      email:    { type: 'string' },
      password: { type: 'string' },
    },
  },
};

fastify.post('/api/users', { schema: createUserSchema }, async (request, reply) => {
  return { message: 'User created' };
});

The schema goes in the route options (second argument) under the schema key. Inside schema, the body key says "this part validates the request body".

What a validation error looks like

In the video, password was changed to { type: 'number' } and a string was sent. Fastify replied automatically with 400 Bad Request, and the handler never ran:

{
  "statusCode": 400,
  "code": "FST_ERR_VALIDATION",
  "error": "Bad Request",
  "message": "body/password must be number"
}

What you can validate

Schema key Validates Example URL / source
body Request body JSON in POST/PUT/PATCH
querystring Query params /api/users?q=john&limit=10
params Route params /api/users/:id
headers Request headers authorization, content-type
response Output, per status code Section 8

A stronger, production-style schema (Beyond the video)

const createUserSchema = {
  body: {
    type: 'object',
    required: ['name', 'email', 'password'],
    additionalProperties: false,               // strip unknown fields
    properties: {
      name:     { type: 'string', minLength: 2, maxLength: 50 },
      email:    { type: 'string', format: 'email' },
      password: { type: 'string', minLength: 8 },
    },
  },
};

const listUsersSchema = {
  querystring: {
    type: 'object',
    properties: {
      q:     { type: 'string' },
      limit: { type: 'integer', minimum: 1, maximum: 100, default: 20 },
    },
  },
};

const getUserSchema = {
  params: {
    type: 'object',
    required: ['id'],
    properties: { id: { type: 'string', pattern: '^[a-f0-9]{24}{{BODY}}#39; } }, // MongoDB ObjectId format
  },
};

Fastify's default Ajv settings (good to know)

Setting Default Effect
coerceTypes 'array' Converts types where possible: ?limit=10 arrives as the string "10" but becomes the number 10 if the schema says integer.
useDefaults true Fills in default values for missing fields.
removeAdditional true Removes unknown fields, but only when the schema has additionalProperties: false.
allErrors false Stops at the first error (faster, and safer against attack payloads).
Remember
  • If you leave out required, every field is optional, even ones listed in properties.
  • The schema checks types but does not strip unknown fields by default. In the video, an extra "age": 30 was sent and still showed up in request.body. Add additionalProperties: false to remove such fields.
  • Validation happens before the handler, so the handler can trust request.body.

8. Response schema & status codes

Why a response schema?

  1. Security: only the fields you list are sent. You can never accidentally leak password or internal fields.
  2. Speed: Fastify uses the schema to build JSON with fast-json-stringify, which is much faster than JSON.stringify.
  3. Documentation: the schema describes exactly what the API returns (tools like @fastify/swagger can turn it into docs).

Example from the video

const createUserSchema = {
  body: { /* ...same as before... */ },
  response: {
    201: {
      type: 'object',
      properties: {
        id: { type: 'string' },
      },
    },
  },
};

fastify.post('/api/users', { schema: createUserSchema }, async (request, reply) => {
  reply.code(201);                          // must match the schema key!
  return { id: 'some-id', name: 'Coder' };  // "name" is NOT sent; only "id"
});

What happened step by step in the video

  1. A response schema for 200 with only id was added, but the handler returned { message }. The response came back empty ({}), because message isn't in the schema.
  2. The handler then returned { id: 'some-id' }, and id appeared.
  3. The schema was changed to 201 (the correct code for "created"), but the reply still used the default 200, so the 201 schema wasn't used.
  4. reply.code(201) was added, so the status became 201 and the schema applied again.
  5. name was added to the returned object. It didn't appear, because it's not in the schema.
Rules
  • A response schema only applies when the status code matches its key.
  • Fields not in properties are silently removed from the output.
  • Set the status with reply.code(n) (or reply.status(n)).
  • You can use ranges as keys: '2xx', '4xx'.

Array response (for "list users")

const userListResponse = {
  200: {
    type: 'array',
    items: {
      type: 'object',
      properties: {
        _id:   { type: 'string' },
        name:  { type: 'string' },
        email: { type: 'string' },
        // no password → it is never sent
      },
    },
  },
};

Status codes you'll use in a REST API

Code Name Use when
200 OK Successful read or update
201 Created A new resource was created (POST)
204 No Content Success with no body (often DELETE)
400 Bad Request Invalid input (Fastify sends this on validation errors)
401 Unauthorized Missing or invalid token
403 Forbidden Logged in, but not allowed
404 Not Found Resource or route doesn't exist
409 Conflict Duplicate, e.g. email already registered
413 Payload Too Large Upload or body over the limit
415 Unsupported Media Type Content type not supported (e.g. multipart without the plugin)
500 Internal Server Error Unexpected server error

10. MongoDB integration

MongoDB in 30 seconds

SQL term MongoDB term
Database Database
Table Collection (e.g. users)
Row Document (a JSON-like object)
Primary key _id (an ObjectId, created automatically)

An ObjectId is a 12-byte id shown as a 24-character hex string, e.g. 652f1c9e8b3e4a1d2c3b4a5f.

Running MongoDB locally

The video uses a local MongoDB inside Docker:

docker run -d --name mongo -p 27017:27017 mongo:7

MongoDB Compass (a free GUI) is used to see the database and documents.

Install the official plugin

Fastify has official plugins for many databases (Docs → Guides → Database: MySQL, Postgres, MongoDB, Redis, …).

npm install @fastify/mongodb

Connection string

# .env
DB_URL=mongodb://localhost:27017/fastify-auth-service
Part Meaning
mongodb:// Protocol
localhost:27017 Host and port (27017 is MongoDB's default port)
/fastify-auth-service Database name (created automatically on first insert)

For MongoDB Atlas (cloud), the URL looks like mongodb+srv://user:pass@cluster.mongodb.net/dbname.

Register the plugin

// server.js
import fastifyMongo from '@fastify/mongodb';

fastify.register(fastifyMongo, {
  forceClose: true,           // close the DB connection when the server shuts down
  url: process.env.DB_URL,
});
  • register(plugin, options) is the same pattern as for routes. Plugins, hooks and decorators are all registered this way.
  • forceClose: true makes sure the connection doesn't stay open after the server stops.
  • Start the server with --env-file=.env (section 4), or process.env.DB_URL will be undefined.
  • If the server starts with no errors, the connection worked.

What the plugin gives you

fastify.mongo.db The database from the URL
fastify.mongo.client The raw MongoClient
fastify.mongo.ObjectId The ObjectId class (to convert string ids)

Get a collection. This is similar to a "model" in Express + Mongoose:

const userCollection = fastify.mongo.db.collection('users');

11. Create a user (insertOne)

Code from the video

// src/routes/user.js
fastify.post('/api/users', { schema: createUserSchema }, async (request, reply) => {
  const userCollection = fastify.mongo.db.collection('users');
  const { name, email, password } = request.body;

  // TODO: hash the password before storing
  const result = await userCollection.insertOne({ name, email, password });
  const insertedId = result.insertedId;

  fastify.log.info(`User created: ${insertedId}`);

  reply.code(201);
  return { id: insertedId.toString() };
});

Step by step

  1. Get the users collection from the Mongo plugin.
  2. Destructure the validated body.
  3. insertOne saves the document. MongoDB adds _id automatically.
  4. result.insertedId is the new document's ObjectId.
  5. Log it, which helps later when monitoring logs.
  6. Return 201 with the id. The response schema makes sure only id is sent.

In the video, the users collection was created in Compass first (not strictly needed, since MongoDB creates it on first insert). After sending the request, refreshing Compass showed the new document.

Logging correctly

Fastify's logger is pino. Its signature is log.info(object, message), with the object first:

fastify.log.info({ userId: insertedId }, 'User created');   // correct: structured
fastify.log.info(`User created: ${insertedId}`);            // fine: plain message
fastify.log.info('User created', insertedId);               // ✗ the id isn't logged the way you expect

The video hit exactly this problem: plain JavaScript shows no type hints, while TypeScript would show the right signature. Inside handlers, request.log.info(...) is even better because each line includes the request id.

Never store plain passwords

If your database leaks, plain passwords expose every user (and their other accounts where they reuse passwords). Always hash passwords before saving them. The video leaves this as a TODO; here's how to do it.

Hashing passwords with Node's built-in crypto (Beyond the video)

No extra library is needed; scrypt is built into Node:

// src/utils/password.js
import { randomBytes, scrypt as scryptCb, timingSafeEqual } from 'node:crypto';
import { promisify } from 'node:util';

const scrypt = promisify(scryptCb);

export async function hashPassword(password) {
  const salt = randomBytes(16).toString('hex');
  const key = await scrypt(password, salt, 64);
  return `${salt}:${key.toString('hex')}`;      // store salt + hash together
}

export async function verifyPassword(password, stored) {
  const [salt, hashHex] = stored.split(':');
  const key = await scrypt(password, salt, 64);
  return timingSafeEqual(key, Buffer.from(hashHex, 'hex')); // constant-time compare
}

const hashed = await hashPassword(password);
await userCollection.insertOne({ name, email, password: hashed });

Popular alternatives are bcrypt and argon2.

Unique email (Beyond the video)

The video noticed that the same email was inserted three times. Fix it with a unique index and handle the duplicate error:

// once, at startup (e.g. in server.js after register, inside fastify.ready or an onReady hook)
await fastify.mongo.db.collection('users').createIndex({ email: 1 }, { unique: true });

try {
  const result = await userCollection.insertOne({ name, email, password: hashed });
  reply.code(201);
  return { id: result.insertedId.toString() };
} catch (err) {
  if (err.code === 11000) {                      // MongoDB duplicate key error
    return reply.code(409).send({ message: 'Email already registered' });
  }
  throw err;                                     // let Fastify return 500
}

12. List users + search with a query param

Get all users

fastify.get('/api/users', async (request, reply) => {
  const userCollection = fastify.mongo.db.collection('users');
  const users = await userCollection.find().toArray();
  fastify.log.info('User list returned');
  return users;
});
  • find() returns a cursor, a lazy pointer to the results. It doesn't load anything yet.
  • .toArray() loads all matching documents into an array.
  • In the video, findOne was typed first by mistake. findOne returns only one document; use find for a list.
  • The first attempt also failed with users is not defined because of a variable name typo. Make sure the name you return matches the name you declared.

Search with ?q=

Goal: GET /api/users?q=john returns only users whose name contains "john".

fastify.get('/api/users', async (request, reply) => {
  const userCollection = fastify.mongo.db.collection('users');
  const { q } = request.query;                // { q: 'john' }

  let query = {};                             // empty filter = match everything
  if (q) {
    query = { name: { $regex: q, $options: 'i' } };
  }

  const users = await userCollection.find(query).toArray();
  return users;
});

How it works:

Piece Meaning
request.query Object built from the query string. ?q=john → { q: 'john' }
{} filter Matches every document, so with no q all users are returned
$regex: q MongoDB operator: field must match this regular expression
$options: 'i' Case-insensitive: "John", "JOHN" and "john" all match

Results from the video: ?q=john returned only "John Doe"; ?q=joh (a partial name) also returned "John Doe", because the regex matches anywhere in the name.

In Postman, add query params in the Params tab (key q, value john). Postman adds ?q=john to the URL for you.

Improvements (Beyond the video)

const escapeRegex = (s) => s.replace(/[.*+?^${}()|[\]\\]/g, '\\{{BODY}}amp;');

fastify.get('/api/users', { schema: listUsersSchema }, async (request, reply) => {
  const { q, limit } = request.query;
  const query = q ? { name: { $regex: escapeRegex(q), $options: 'i' } } : {};

  return fastify.mongo.db.collection('users')
    .find(query, { projection: { password: 0 } })  // never return passwords
    .limit(limit)                                   // pagination
    .toArray();
});
  • Escape user input before putting it in a regex. Otherwise characters like .* change the meaning, and crafted patterns can make the database slow (ReDoS).
  • projection: { password: 0 } excludes the password field at the database level.
  • limit stops one request from loading thousands of documents.

13. Route params: get a single user by id

Dynamic params

:id in a URL is a dynamic segment: it matches any value, and that value appears in request.params.

// GET /api/users/652f1c9e8b3e4a1d2c3b4a5f
fastify.get('/api/users/:id', async (request, reply) => {
  const userCollection = fastify.mongo.db.collection('users');
  const id = new fastify.mongo.ObjectId(request.params.id);  // string → ObjectId

  const user = await userCollection.findOne({ _id: id });
  return user;
});

Why convert to ObjectId?

URL params always arrive as strings. MongoDB stores _id as an ObjectId type, and the string "652f…" is not equal to ObjectId("652f…"), so findOne would find nothing. new fastify.mongo.ObjectId(str) converts it.

In Postman, duplicate the "List Users" request, rename it Get User, and use http://localhost:4000/api/users/<paste an _id>. Changing the id returns a different user.

Params vs query, side by side

Params Query
Declared in route? Yes: /users/:id No
URL /api/users/652f… /api/users?q=john
Access request.params.id request.query.q
Required? Yes, part of the path Optional
Use for Identifying one resource Filtering, searching, sorting, pagination

Handle invalid and missing ids (Beyond the video)

fastify.get('/api/users/:id', async (request, reply) => {
  const { id } = request.params;
  if (!fastify.mongo.ObjectId.isValid(id)) {
    return reply.code(400).send({ message: 'Invalid user id' });
  }

  const user = await fastify.mongo.db.collection('users')
    .findOne({ _id: new fastify.mongo.ObjectId(id) }, { projection: { password: 0 } });

  if (!user) {
    return reply.code(404).send({ message: 'User not found' });
  }
  return user;
});
Warning

new ObjectId('abc') throws for an invalid string, and without a check the client gets a 500. Check with ObjectId.isValid() (or validate with a params schema) and return 400 instead.

14. Update and delete (Beyond the video)

The video mentioned building CRUD (Create, Read, Update, Delete) but only covered create and read. Here are the other two, following the same pattern:

// PATCH /api/users/:id   body: { "name": "New Name" }
fastify.patch('/api/users/:id', async (request, reply) => {
  const _id = new fastify.mongo.ObjectId(request.params.id);
  const result = await fastify.mongo.db.collection('users')
    .updateOne({ _id }, { $set: request.body });   // $set changes only the given fields

  if (result.matchedCount === 0) {
    return reply.code(404).send({ message: 'User not found' });
  }
  return { message: 'User updated' };
});

// DELETE /api/users/:id
fastify.delete('/api/users/:id', async (request, reply) => {
  const _id = new fastify.mongo.ObjectId(request.params.id);
  const result = await fastify.mongo.db.collection('users').deleteOne({ _id });

  if (result.deletedCount === 0) {
    return reply.code(404).send({ message: 'User not found' });
  }
  return reply.code(204).send();                   // success, no body
});
Warning

Give the PATCH body a schema with additionalProperties: false, or a client could $set fields like role: 'admin'.

15. Hooks: Fastify's middleware

The problem

Some routes should only be available to authenticated users (users who send a valid token). We need code that runs before the handler, checks the token, and either lets the request continue or rejects it.

In Express this is called middleware. In Fastify it's done with hooks.

The request lifecycle

Every request passes through fixed stages, in order. A hook is your own function that runs at one of those stages (Docs → Reference → Lifecycle and Hooks).

Incoming request
  │
  ▼
onRequest          ← very first; body not parsed yet (good for early auth checks)
  │
preParsing         ← before the body is parsed (can transform the raw stream)
  │
  (body parsing)
  │
preValidation      ← body parsed, not yet validated
  │
  (schema validation)
  │
preHandler         ← validated, just before your handler  ⭐ used in the video
  │
  ▼
HANDLER            ← your route function
  │
preSerialization   ← before the returned object is turned into JSON
  │
onSend             ← before the response is sent (can change the payload/headers)
  │
onResponse         ← after the response was sent (logging, metrics)
Hook Runs Typical use
onRequest First, before parsing Auth checks that don't need the body, rate limiting
preParsing Before the body is parsed Decompress or transform the raw body
preValidation After parsing, before validation Change the body before the schema checks it
preHandler After validation, before the handler Auth, permission checks, loading the user
preSerialization After the handler, before JSON Wrap every response in { data: ... }
onSend Before sending Add headers, compress
onResponse After sending Logging, metrics
onError When an error happens Custom error logging
onTimeout When a request times out Monitoring

There are also application hooks that run for the app, not per request: onReady, onListen, onClose, preClose, onRoute, onRegister.

Adding a hook

fastify.addHook('preHandler', (request, reply, done) => {
  console.log('Checking auth');
  done();   // continue to the next step of the lifecycle
});
Argument Meaning
request, reply Same objects the handler gets
done Callback you must call to hand control to the next stage (like next() in Express)

What the video demonstrated

  1. With done() not called, sending "Get User" in Postman made the request hang: no response ever arrived.
  2. After adding done(), the response came back and Checking auth appeared in the terminal.
Forgot done()? The request hangs

In callback-style hooks, if you neither call done() nor send a reply, the request is stuck forever. Every code path must end in done(), done(err), or reply.send().

16. Hook scopes: global, plugin, route

Where you add a hook decides which routes it runs for. This comes from plugin encapsulation (section 6).

Registered in… Applies to Example
server.js, on the root instance All routes in the app Request logging, CORS
Inside a plugin (e.g. userRouter) Every route in that plugin (and its children) All user routes need auth
Route options { preHandler: fn } Only that route Only "get user" needs auth

1. Global

// server.js
fastify.addHook('preHandler', (request, reply, done) => {
  request.log.info('runs for every route');
  done();
});

2. Plugin level

// src/routes/user.js
async function userRouter(fastify) {
  fastify.addHook('preHandler', (request, reply, done) => {
    console.log('Checking auth');   // runs for ALL routes below
    done();
  });

  fastify.get('/api/users', ...);      // ✓ hook runs
  fastify.get('/api/users/:id', ...);  // ✓ hook runs
}

In the video, both "List Users" and "Get User" printed Checking auth, which proved the hook applied to the whole router.

3. Route level (what the video settled on)

First move the hook into its own file, which keeps routes clean and makes the hook reusable:

// src/hooks/auth.js
export const authHandler = (request, reply, done) => {
  console.log('Checking auth');
  done();
};

Then attach it to just one route through the options object (the same object where schema goes):

// src/routes/user.js
import { authHandler } from '../hooks/auth.js';   // remember .js

fastify.get('/api/users/:id', { preHandler: authHandler }, async (request, reply) => {
  // ...
});

Result in the video: "Get User" printed Checking auth, while "List Users" didn't.

Tip

preHandler (and other hooks in route options) also accepts an array: { preHandler: [authHandler, adminOnly] }. They run in order.

17. Async hooks & authentication

Two styles of hooks

Callback style Async style
Signature (request, reply, done) async (request, reply)
Continue Call done() Just let the function finish (the promise resolves)
Fail with error done(err) throw err
Reply early reply.send(...), don't call done reply.send(...) then return reply
Can use done? Yes, required No. Mixing the two is an error
Warning

If a hook is async, don't use done. Fastify waits for the returned promise: if it resolves, the request continues; if it rejects (throws), the request fails.

The video's example: callback hook + promise-based token check

First, a fake token check that returns a promise (in a real app this would verify a JWT):

// src/hooks/auth.js
const validateToken = () => {
  return new Promise((resolve, reject) => {
    // token check logic here...
    // if everything is OK:
    resolve({ userId: '123' });
    // if the token is bad:
    // reject(new Error('User token is invalid'));
  });
};

Then a callback-style hook that uses it with .then() / .catch():

export const authHandler = (request, reply, done) => {
  console.log('Checking auth');

  validateToken()
    .then((user) => {
      request.userId = user.userId;   // attach user data for the handler
      done();                         // continue to the handler
    })
    .catch((err) => {
      // Way 1: pass the error to done()
      reply.code(401);                // without this line, the client gets 500
      done(err);

      // Way 2 (alternative): reply directly with custom data. Don't call done.
      // reply.code(401).send({ success: false });
    });
};

And in the handler:

fastify.get('/api/users/:id', { preHandler: authHandler }, async (request, reply) => {
  console.log('From user handler', request.userId);   // "123"
  // ...
});

What the video tested

Scenario Result
Promise resolves Handler runs; From user handler logged; response 200
Promise rejects, done(err) 500 { "message": "User token is invalid" }; handler not run
Rejects, reply.code(401) + done(err) 401 with the same message
Rejects, reply.code(401).send({ success: false }) 401 { "success": false }; handler not run
Resolves with { userId } request.userId available in the handler ("123" logged)

Passing data from a hook to the handler

Setting request.userId = ... in a hook is how the logged-in user reaches the handler. Fastify recommends declaring the property first with a decorator, which keeps object shapes stable (and fast):

// in server.js or the plugin, before routes
fastify.decorateRequest('userId', null);

The same hook in async style

Cleaner, with no done and no .then chains:

export const authHandler = async (request, reply) => {
  try {
    const user = await validateToken();
    request.userId = user.userId;           // continue automatically
  } catch {
    return reply.code(401).send({ success: false, message: 'Invalid token' });
  }
};

18. File upload (multipart)

Why a plugin is needed

Normal API requests send JSON (Content-Type: application/json). File uploads send multipart/form-data, a format that splits the body into parts (files and text fields).

Fastify only parses JSON (and plain text) by default. In the video, sending a file before installing the plugin returned:

415 Unsupported Media Type

Install and register the official plugin

npm install @fastify/multipart

// src/routes/user.js (only these routes), or server.js (the whole app)
import multipart from '@fastify/multipart';

fastify.register(multipart, {
  limits: {
    fieldNameSize: 100,     // max length of a field name (bytes)
    fieldSize: 100,         // max size of a text field value (bytes)
    fields: 10,             // max number of text fields
    fileSize: 1_000_000,    // max file size (bytes) → ~1 MB
    files: 1,               // max number of files
    headerPairs: 2000,      // max number of header key-value pairs
  },
});
Limit Protects against
fileSize Huge uploads filling your disk or memory
files Someone sending hundreds of files at once
fields / fieldSize Huge or numerous text fields
fieldNameSize / headerPairs Malformed or abusive requests

All sizes are in bytes: 1 KB = 1,024 bytes, 1 MB ≈ 1,000,000 bytes.

The upload route

import fs from 'node:fs';
import { pipeline } from 'node:stream/promises';

fastify.post('/api/upload', async (request, reply) => {
  const data = await request.file();   // method added by @fastify/multipart

  await pipeline(
    data.file,                                         // source: incoming stream
    fs.createWriteStream(`static/${data.filename}`),   // destination: file on disk
  );

  return { message: 'File uploaded' };
});

What's inside data

In the video, console.log(data) printed a large object. The important parts:

Property Example Meaning
data.file Readable stream The file's contents, arriving piece by piece
data.filename photo.jpg Original file name from the client
data.mimetype image/jpeg File type
data.fieldname image Name of the form field
data.encoding 7bit Transfer encoding
data.fields { ... } Other fields in the same form

Streams and pipeline explained

A stream delivers data in small chunks instead of all at once. For files this matters: a 500 MB video would need 500 MB of RAM if loaded fully, but as a stream it only needs a few KB at a time.

  • data.file is a readable stream (data comes in).
  • fs.createWriteStream(path) creates a writable stream (data goes out to a file).
  • pipeline(source, destination) connects them. It moves chunks from one to the other, handles backpressure (slowing down if the disk is slower than the network), and cleans up both streams if anything fails.
  • We import the promise version from node:stream/promises, so we can await it.

Testing in Postman

  1. New request Upload, method POST, URL http://localhost:4000/api/upload.
  2. Body tab → form-data.
  3. Add a key (e.g. image), change its type from Text to File, and pick an image from your computer.
  4. Send. The file appears in the static/ folder with its original name.
Before you test

The static/ folder must exist, or createWriteStream fails with ENOENT. Create it by hand or in code: fs.mkdirSync('static', { recursive: true }).

Safer production version (Beyond the video)

The video mentions that real apps don't keep the original file name; they generate a UUID. Here's why and how:

  • Two users uploading photo.jpg would overwrite each other.
  • A malicious file name like ../../server.js could write outside the folder (path traversal).
  • The client can lie about the type, so check mimetype against an allow-list.
import { randomUUID } from 'node:crypto';

const ALLOWED = { 'image/jpeg': 'jpg', 'image/png': 'png', 'image/webp': 'webp' };

fastify.post('/api/upload', async (request, reply) => {
  const data = await request.file();
  if (!data) {
    return reply.code(400).send({ message: 'No file sent' });
  }
  if (data.fieldname !== 'image') {
    return reply.code(400).send({ message: 'Field "image" is required' });
  }

  const ext = ALLOWED[data.mimetype];
  if (!ext) {
    return reply.code(415).send({ message: 'Only JPG, PNG or WEBP allowed' });
  }

  const name = `${randomUUID()}.${ext}`;
  await pipeline(data.file, fs.createWriteStream(`static/${name}`));
  return reply.code(201).send({ file: name });
});
  • If a file exceeds fileSize, the plugin throws, and Fastify returns 413 Payload Too Large by default.
  • For multiple files, loop over request.files(): for await (const part of request.files()) { ... }.
  • To serve uploaded files back to clients, use @fastify/static:
import fastifyStatic from '@fastify/static';
import path from 'node:path';

fastify.register(fastifyStatic, {
  root: path.join(import.meta.dirname, 'static'),
  prefix: '/static/',          // GET /static/<name>.jpg
});

const createUserSchema = {
  body: {
    type: 'object',
    required: ['name', 'email', 'password'],
    properties: {
      name: { type: 'string' },
      email: { type: 'string' },
      password: { type: 'string' },
    },
  },
  response: {
    201: {
      type: 'object',
      properties: {
        id: { type: 'string' },
      },
    },
  },

async function userRouter(fastify, options) {
  fastify.register(multipart, {
    limits: {
      fieldNameSize: 100,
      fieldSize: 100,
      fields: 10,
      fileSize: 1_000_000,
      files: 1,
      headerPairs: 2000,
    },
  });

  // Create user
  fastify.post('/api/users', { schema: createUserSchema }, async (request, reply) => {
    const userCollection = fastify.mongo.db.collection('users');
    const { name, email, password } = request.body;

    // TODO: hash the password before storing
    const result = await userCollection.insertOne({ name, email, password });
    const insertedId = result.insertedId;

    fastify.log.info(`User created: ${insertedId}`);

    return { id: insertedId.toString() };

    const userCollection = fastify.mongo.db.collection('users');
    const { q } = request.query;

    let query = {};
    if (q) {
      query = { name: { $regex: q, $options: 'i' } };
    }

    const users = await userCollection.find(query).toArray();
    fastify.log.info('User list returned');
    return users;
  });

  // Get one user (protected by authHandler)
  fastify.get('/api/users/:id', { preHandler: authHandler }, async (request, reply) => {
    console.log('From user handler', request.userId);
    const userCollection = fastify.mongo.db.collection('users');
    const id = new fastify.mongo.ObjectId(request.params.id);

    const user = await userCollection.findOne({ _id: id });
    return user;
  });

  // Upload a file
  fastify.post('/api/upload', async (request, reply) => {
    const data = await request.file();
    await pipeline(data.file, fs.createWriteStream(`static/${data.filename}`));

Route hook { preHandler: fn } or [fn1, fn2]
Callback hook (req, reply, done) => { done() }
Async hook async (req, reply) => { /* throw to fail */ }
File upload await request.file() + pipeline(data.file, fs.createWriteStream(path))
Express middleware await register(@fastify/express) then fastify.use(mw)

25. Self-check quiz

Why is Fastify faster than Express?

A radix-tree router (find-my-way), compiled schema validation (Ajv), schema-based JSON serialization (fast-json-stringify), the pino logger, and low overhead per request.

What does "type": "module" do?

It lets you use import / export (ES modules) instead of require. Local imports then need the .js extension.

Why does the server log two "listening" lines?

localhost resolves to both IPv6 (::1) and IPv4 (127.0.0.1), and Fastify listens on both.

Do you need reply.send() in an async handler?

No. Just return the object and Fastify serializes and sends it. Don't do both.

What is a plugin, and how do you add one?

A function (fastify, options) that adds routes, hooks or decorators. Add it with fastify.register(plugin, options).

Why is fastify.mongo visible inside the user routes plugin?

@fastify/mongodb is wrapped with fastify-plugin, which breaks encapsulation and shares the decorator with the whole app.

What happens if the schema has no required array?

Every field is optional.

Does the schema remove extra body fields?

Not by default. Add additionalProperties: false; Fastify's Ajv then strips them.

What does the client get when validation fails?

A 400 with code: FST_ERR_VALIDATION and a message like body/password must be number. The handler doesn't run.

The response schema is for 201 but every field is sent. Why?

The reply is still 200. Call reply.code(201) so the matching schema applies.

Why must a string id be converted to ObjectId?

MongoDB stores _id as an ObjectId type; a string never equals it, so findOne returns null.

What does $options: 'i' mean in a regex query?

Case-insensitive matching.

Params vs query?

/users/:id gives request.params.id (identifies one resource); ?q=x gives request.query.q (filters or searches).

Which hook runs right before the handler?

preHandler.

Why does a callback-style hook make the request hang?

done() was never called and no reply was sent, so the lifecycle never continues.

Can you use done inside an async hook?

No. Resolve to continue; throw or reply.send() + return reply to stop.

How do you apply a hook to only one route?

Pass it in the route options: { preHandler: authHandler }.

What does done(err) return to the client if no status code is set?

500, with the error message. Set reply.code(401) first to return 401.

How does the handler know which user is logged in?

The hook attaches it to the request (request.userId = ...), ideally declared first with fastify.decorateRequest('userId', null).

Why do you get 415 on upload?

Fastify only parses JSON by default. Register @fastify/multipart.

Why use pipeline instead of reading the whole file?

Streams process the file in small chunks (low memory), pipeline handles backpressure, and it cleans up if something fails.

Why not save uploads with the original file name?

Name clashes overwrite files, and names like ../ can escape the folder (path traversal). Generate a UUID name instead.

How do you use an Express middleware in Fastify?

await fastify.register(fastifyExpress) (from @fastify/express), then fastify.use(middleware).
